# ADR-742 — «Ανήκει ΑΥΤΟ το έγγραφο;»: μία ερώτηση, ένα δόγμα αποκάλυψης

- **Κατάσταση:** Φάση Α ✅ υλοποιημένη (commit `01f8dcbc`) · Φάση Β ✅ υλοποιημένη · Φάσεις Γ+Δ ⏸️
- **Ημερομηνία:** 2026-07-31
- **Σχετικά:** ADR-255 (per-document ownership — απορροφάται), ADR-232 (έγγραφα υπεργραφείου),
  ADR-702 (tenant query scope — **ΔΕΝ** ενοποιείται), ADR-356 (super-admin scope — **ΔΕΝ** ενοποιείται),
  ADR-699 (share resolvers), ADR-734 §7.1 (το ίδιο δόγμα, ήδη γραμμένο για το στρώμα του πράκτορα)

## 1. Το πρόβλημα

Η ερώτηση **«ανήκει αυτό το έγγραφο στον πελάτη που ρωτάει;»** ήταν γραμμένη σε
**τέσσερα** ανεξάρτητα συστήματα, από πέντε διαφορετικές στιγμές:

| # | Πού | Τι ήταν |
|---|---|---|
| 1 | `lib/auth/tenant-isolation.ts` (ADR-255, Ιαν 2026) | 6 φύλακες — **το ίδιο 20γραμμο block αντιγραμμένο 6 φορές μέσα στο ίδιο αρχείο** |
| 2 | `lib/auth/tenant-ownership.ts` (2026-07-30) | καθαρό module, γραμμένο από κάποιον που **δεν έβλεπε** το #1 |
| 3 | `services/sharing/resolver-core/share-entity-access.ts:78` | `=== user.companyId`, client SDK |
| 4 | `lib/firestore/entity-creation.service.ts:132` | ίδιος έλεγχος για ήδη διαβασμένο γονέα |

Συν `filterSnapshotsByTenant` που την ξανάγραφε για παρτίδες, και **46 αρχεία**
με χειρόγραφο `x.companyId !== ctx.companyId`.

### 🔴 Η αιτία — και είναι η μόνη που έχει σημασία

**Το `tenant-isolation.ts` δεν είχε ποτέ καταχώρηση στο `.ssot-registry.json`.**

Κανένα gate δεν φύλαγε την περιοχή· κανένα `ssot:discover` δεν το ανέδειξε. Έτσι,
τον Ιούλιο, κάποιος έγραψε καλόπιστα ένα δεύτερο καθαρό module για το ίδιο
πράγμα — δεν υπήρχε τρόπος να το βρει.

> **Ένα SSoT χωρίς εγγραφή στο μητρώο δεν είναι SSoT — είναι απλώς ένα αρχείο.**

Ίδιο σχήμα με το «0 = κανείς δεν κοίταξε» των N.11/N.12. Αν αυτό το ADR κάνει
μόνο ένα πράγμα σωστά, είναι **η καταχώρηση στο μητρώο**, όχι η ενοποίηση.

## 3. Η απόφαση

### 3.1 Ο πυρήνας — καθαρός επίτηδες

`lib/auth/tenant-ownership.ts`: **μηδέν Firebase, μηδέν `server-only`.**

Αυτό δεν είναι αισθητική. Είναι η προϋπόθεση για να μοιράζονται **την ίδια
σύγκριση** ο browser (share resolvers, `boq-repository`) και το Admin SDK.

> Το σχόλιο του ADR-699 έλεγε ότι η ενοποίηση «θα έσερνε το `firebase-admin` σε
> client bundle». Ήταν **σωστό για τα περιβλήματα** και **λάθος για τη σύγκριση
> δύο strings** — και ακριβώς η σύγκριση ήταν αυτή που είχε διπλασιαστεί.
> Το επιχείρημα του bundle κάλυπτε, χωρίς να το θέλει, ένα χειρόγραφο αντίγραφο.

### 3.2 Τρεις **ονομασμένες** έννοιες, όχι σημαίες

Μια boolean σε κλήση ασφαλείας είναι αυτό που ρυθμίζεται λάθος στο review:

| Συνάρτηση | Τι κάνει |
|---|---|
| `isOwnedByCompany` / `isPayloadOwnedByCompany` | **η ερώτηση**, χωρίς παρενέργειες |
| `ownedOrNull` | **σιωπηλή** πολιτική — ξένο ≡ ανύπαρκτο· **δεν μαρτυρά ύπαρξη** |
| `assertOwnedByCompany` | **ρητή άρνηση** — **μαρτυρά ύπαρξη**, συνειδητή ανταλλαγή |
| `concealCrossTenant` | **η απόφαση αποκάλυψης** στο σύνορο HTTP |

### 3.3 Ο κανόνας αποκάλυψης

> **«Θα μπορούσε ο καλών να το μάθει νόμιμα με άλλον τρόπο;»**
> Ναι → πες την αλήθεια (403). Όχι → σιώπησε (404).

**ΟΧΙ** «διάλεξε κωδικό». **ΟΧΙ** «να είμαστε ομοιόμορφοι».

Στον Νέστορα το `list` είναι πάντα tenant-scoped → κανονικός χρήστης δεν μπορεί
ποτέ να μάθει νόμιμα ότι υπάρχει ξένο id → **σιωπή**. Ο bypass ρόλος έχει ήδη
cross-tenant ορατότητα → **ειλικρινές 403**, που του σώζει τη διάγνωση.

⚠️ Η εξαίρεση super-admin **δεν είναι νέο δόγμα** — είναι ήδη αυτό που κάνει το
`tenant-isolation.ts` στις έξι `require*InTenant`. **Ευθυγραμμίζεται, δεν εισάγεται.**

#### Πηγές (έρευνα 2026-07-31)

| Πλατφόρμα | Γραμμή |
|---|---|
| **GitHub** | 404 — ρητά «to avoid confirming the existence of private repositories» |
| **Google Drive** | 404 — το `notFound` καλύπτει σκόπιμα και τα δύο |
| **Figma** | 404 — άλλαξε **από** 403 και δεν το γύρισε πίσω παρά τις διαμαρτυρίες |
| **Autodesk APS** | 403/404 διακριτά — το πλησιέστερο CAD/BIM **δεν** ακολουθεί (B2B με ρητό project membership) |
| **OWASP / IDOR** | 404 για μη-δημόσιους πόρους |
| 🏆 **AWS S3** | **παράγει** τον κανόνα: έχεις `s3:ListBucket` → 404· δεν έχεις → 403 ακόμη κι όταν λείπει |

### 3.4 🔑 Η κρίσιμη σχεδιαστική απόφαση (Φάση Β)

> Η **υπηρεσία** ρίχνει **πάντα** τυποποιημένο `CrossTenantAccessError` (αλήθεια).
> Το **route** αποφασίζει τι φεύγει στο σύρμα.

- Μηδέν αλλαγή υπογραφών στα services
- Η απόφαση ζει στο **σύνορο αποκάλυψης** — το μόνο στρώμα που ξέρει *ποιος* ρωτάει
- Εσωτερικοί καλούντες και logs κρατούν πλήρη εικόνα

⚠️ **Το μεταμφιεσμένο 404 πρέπει να είναι ΠΑΝΟΜΟΙΟΤΥΠΟ με το γνήσιο.** Αν το
γνήσιο λέει `Text template not found: tpl_x` και το ψεύτικο σκέτο `Not found`,
**το ίδιο το κείμενο γίνεται μαντείο**. Παράγεται από τον **ίδιο constructor**.

## 4. Ένα πραγματικό σφάλμα που διορθώθηκε στην πορεία

Και οι τέσσερις χειρόγραφες μορφές απαντούσαν **`true`** όταν το έγγραφο **και**
ο καλών είχαν κενό `companyId`:

```ts
snap.data().companyId === user.companyId   // '' === ''  ⇒  true
```

Καλών με χαλασμένο token (`companyId: ''`) έβλεπε κάθε έγγραφο με κενό
`companyId`. Το `isPayloadOwnedByCompany` αντιμετωπίζει το κενό ως **απουσία**
tenant, ποτέ ως tenant που τυχαίνει να ταιριάζει.

## 7. Τι υλοποιήθηκε στη Φάση Β (2026-07-31)

Και τα τέσσερα endpoints περνούν πλέον από `concealCrossTenant`.

### 7.1 Το σχήμα που εφαρμόστηκε — και γιατί αυτό

> Η ταυτότητα γνήσιου και μεταμφιεσμένου 404 δεν είναι **θέμα προσοχής**· είναι **δομική**.

Κάθε διαδρομή δίνει **ένα** `notFound` callback που εξυπηρετεί **και τους δύο** κλάδους:

```ts
backgroundErrorResponse({ err, ctx, notFound: () => backgroundNotFoundResponse(id) })
// conceal: notFound   ← το ΙΔΙΟ callback, όχι δεύτερη γραφή του ίδιου σώματος
```

Δεν υπάρχει τρόπος να αποκλίνουν χωρίς να αλλάξουν **και τα δύο**. Αυτό κατοχυρώνεται με `toEqual` —
όχι «μοιάζει», **ίσο**.

Παραμετροποιείται επειδή το `DELETE` έχει δικό του σχήμα (`{ deleted: false }`): η μεταμφίεση ακολουθεί
**το σχήμα της διαδρομής**, αλλιώς το σχήμα και μόνο θα πρόδιδε τη διαφορά.

### 7.3 Λάθος #2: «cross-tenant» και «locked» στον ίδιο κλάδο

Το `[id]/route.ts:154` έγραφε `msg.includes('Cross-tenant') || msg.includes('locked')` και έβγαζε **και τα
δύο** ως `409 FORBIDDEN`. Είναι **αντίθετα**:

- «locked» μαρτυρά ότι ο πόρος **υπάρχει και σου ανήκει** — πληροφορία που ο χρήστης δικαιούται
- «cross-tenant» είναι **ακριβώς** αυτό που δεν επιτρέπεται να μαρτυρηθεί

Πλέον `BackgroundLockedError` → ξεχωριστό `409 LOCKED`, **χωρίς** μεταμφίεση.

### 7.4 Το string-matching ως έλεγχος πρόσβασης

`msg.includes('Cross-tenant')` ήταν **δύο** ζωντανά σημεία — όχι τρία· το `floor-wipe-queries.ts` απλώς
logger-άρει. Μια αθώα αλλαγή διατύπωσης σε μήνυμα υπηρεσίας θα μετέτρεπε **σιωπηλά** την άρνηση ασφαλείας
σε `500`. Τώρα είναι **μηδέν**, και το `includes\('Cross-tenant'\)` μπήκε **4ο `forbiddenPattern`** στο
module `tenant-document-ownership`.

⚠️ Το `isRoleBypass(` **δεν** μπήκε: έχει ~80 νόμιμες χρήσεις RBAC — θα ήταν θόρυβος, όχι σήμα.

### 7.5 🔴 Τρύπα που η Φάση Α είχε αφήσει ανοιχτή — τη βρήκε test

Η §4 περιγράφει το σφάλμα του κενού `companyId`. Η Φάση Α το έκλεισε **μόνο στο σιωπηλό μονοπάτι**
(`isPayloadOwnedByCompany` → οι έξι `require*InTenant`). Η `assertOwnedByCompany` συνέχιζε να ρωτά με
σκέτο `===`, ενώ **και οι τέσσερις** καλούντες της της δίνουν `snap.data() as XDoc`:

> ο **τύπος υπόσχεται** `companyId: string`· η **βάση δεν το εγγυάται**. Το `as` ήταν το ψέμα.

Καλών με χαλασμένο token (`companyId: ''`) περνούσε σε κάθε έγγραφο με κενό `companyId`. Η υπογραφή
δέχεται πλέον `MaybeTenantOwned` και ρωτά `isPayloadOwnedByCompany` — μία αλλαγή, τέσσερα σημεία κλήσης
διορθωμένα, μηδέν αλλαγή στους καλούντες.

**Το βρήκε ένα test της Φάσης Β, όχι ανάγνωση κώδικα.** Δύο συνεδρίες είχαν διαβάσει αυτή τη συνάρτηση.

### 7.8 Ο εκτελεστής route — γιατί έγινε κι αυτός ένας

Δώδεκα endpoints έγραφαν το **ίδιο** δεκάγραμμο κέλυφος: ρυθμιστής ρυθμού → ταυτότητα → δικαιώματα →
`try/catch` → καταγραφή → χαρτογράφηση. Το `jscpd` το μετρούσε ως clones **ήδη στο HEAD**, οπότε
οτιδήποτε άγγιζε κανείς εκεί έκοβε το CHECK 3.28.

Δεν είναι «λίγος κώδικας που μοιάζει» — είναι η **αλυσίδα ασφαλείας** κάθε endpoint. Αν ένα αντίγραφο
ξεχάσει τον ρυθμιστή ρυθμού ή τυλίξει το `try/catch` λίγο πιο μέσα, η διαφορά **δεν φαίνεται πουθενά**:
το endpoint απαντά κανονικά, απλώς είναι λιγότερο προστατευμένο από τα αδέλφια του.

⚠️ Ο ρυθμιστής είναι σκόπιμα **καρφωμένος** σε `STANDARD` και δεν παραμετροποιείται: και τα δώδεκα
endpoints είχαν `withStandardRateLimit`. Παράμετρος με μία μόνο τιμή σε όλους τους καλούντες δεν είναι
ευελιξία — είναι πρόσκληση να διαφοροποιηθεί κάποιος αθόρυβα.

🔴 **Ο εκτελεστής είναι το σημείο όπου όλη η απόφαση αποκάλυψης κρέμεται από μία μεταβλητή** — το
`ctx.globalRole` που παραδίδει στη χαρτογράφηση. Ένα καρφωμένο `'super_admin'` εκεί θα άνοιγε ξανά το
μαντείο για **όλο** το πεδίο ορισμού, με κάθε άλλο test πράσινο. Γι' αυτό υπάρχει
`__tests__/domain-route-ctx.test.ts`: μοναδική δουλειά του να αποδεικνύει ότι φτάνει ο **σωστός**
καλών, όχι ένας ρόλος.

### 7.7 ⚠️ Γνωστή ασυμμετρία — δηλωμένη, όχι κρυμμένη

Η εξαίρεση super-admin ισχύει όπου η **υπηρεσία ρίχνει**. Το `FloorplanBackgroundService.getById` είναι
**σιωπηλό για όλους** (συνειδητή απόφαση της Φάσης Α: ξένο ≡ ανύπαρκτο), άρα από εκείνο το μονοπάτι
ούτε ο bypass ρόλος παίρνει `403`. Το να αλλάξει θα απαιτούσε αλλαγή υπογραφής στην υπηρεσία — που το
§3.4 ρητά αποκλείει.

## 7ter. Η σάρωση Γ+Δ — η **αναγνώριση** (2026-07-31)

Ο Γιώργος ενέκρινε **ενιαία** σάρωση Γ+Δ (όχι σε δόσεις ανά domain): το
`forbiddenPattern` μπαίνει μόνο όταν μεταναστεύσουν **όλα**, οπότε οι δόσεις
κυνηγούν κινούμενο στόχο.

### 7ter.1 Τα μετρημένα — **65 σημεία σε 45 αρχεία**

| Κατηγορία | Σημεία | Κριτήριο |
|---|---:|---|
| **Γ** | **52** | ρωτά «ανήκει ΑΥΤΟ;» μετά το read, αρνείται με 403 |
| **Δ** | **10** | ίδια ερώτηση, **ήδη** σιωπά |
| **⛔ ΕΞΩ** | **3** | άλλη ερώτηση μεταμφιεσμένη — δεν αγγίζεται |

🔴 **Το χονδρικό φίλτρο «έχει 403 στο αρχείο» ήταν λάθος και προς τις δύο
κατευθύνσεις.** Από τα 9 «υποψήφια Δ» μόνο **3** ήταν όντως Δ· και βρέθηκαν **6
Δ κρυμμένα μέσα σε αρχεία που είχαν 403** (τα procurement services: το `getX`
σιωπά, το `updateX` ρίχνει, **ίδιο αρχείο**). ⇒ **Η ταξινόμηση απαιτεί ανάγνωση,
όχι grep** — αυτός είναι όλος ο λόγος ύπαρξης του Βήματος 1.

Τα 3 ⛔ ΕΞΩ: δύο **log-only** κλάδοι super-admin (`projects/[projectId]/route.ts`,
`project-mutations.service.ts` — γράφουν log, δεν αποφασίζουν) + το φίλτρο λίστας
του `floorplan-overlays.handlers.ts` πάνω σε **ήδη** tenant-scoped query (ADR-702).
⚠️ Η πρόβλεψη ότι «πολλά projects θα είναι ΕΞΩ λόγω ADR-356» **δεν επιβεβαιώθηκε**:
κανένα `superAdminOverride`, κανένα `resolveSuperAdminProjectScope` — είναι η ίδια
bypass εξαίρεση που κάνει ήδη το `tenant-isolation.ts`.

### 7ter.2 🔴 Ο κλάδος `reveal` είναι **απρόσιτος** στη Γ — δομική διαφορά από τη Β

Στη Φάση Β η υπηρεσία έριχνε **πάντα** και ο bypass ρόλος έπαιρνε ειλικρινές 403.
Τα 52 Γ γράφουν `!isSuperAdmin && companyId !== …`: ο bypass **παίρνει το
έγγραφο**, δεν φτάνει ποτέ σε άρνηση. Αφελής αντικατάσταση με
`assertOwnedByCompany` (που **δεν έχει εξαίρεση super-admin by design**) θα έδινε
403 στον υπεργραφέα ⇒ **παλινδρόμηση**. Το `!isSuperAdmin &&` μένει **έξω** από
την κλήση SSoT· πρακτικά η Γ εδώ είναι «403 → 404 **για τους μη-bypass**».

### 7ter.3 Τι λέει η βιομηχανία για την ασυμμετρία bypass (έρευνα 2026-07-31)

Πέντε σημεία μπλοκάρουν **και** τον super-admin ενώ τα αδέρφια τους όχι
(`contacts/[contactId]/route.ts`, `contacts/…/properties`, `ika/…/insurance-class`,
`parking/route.ts:214` **ενώ το `:98` στο ίδιο αρχείο** έχει bypass,
`admin/role-management/…`). Το ερώτημα «bypass παντού ή πουθενά;» είναι **λάθος
ερώτημα**:

> **Zero Standing Privilege**: καμία μόνιμη, always-on προνομιακή πρόσβαση.
> Cross-tenant admin ενέργειες με **just-in-time elevation, χρονικά φραγμένη,
> ελεγχόμενη** — **ποτέ standing cross-tenant access**.
> Η **Google** το εφαρμόζει στον εαυτό της: «by default, Google does not have
> access to customer data»· το **Access Transparency** καταγράφει ποιος, πότε,
> σε τι και **γιατί**· το **Access Approval** δίνει βέτο στον πελάτη.

⇒ Το `isRoleBypass(ctx.globalRole)` σε **47 από τα 52** σημεία **είναι** standing
cross-tenant privilege, σκόρπιο σε 45 αρχεία, χωρίς λόγο/όριο/audit. Τα 5
«αυστηρά» δεν είναι το σφάλμα — είναι τα **μόνα** που κάνουν το σωστό.

**Απόφαση**: η Γ+Δ **δεν αλλάζει ποιος βλέπει τι** (αλλάζει *τι λέμε* στην
άρνηση)· η ασυμμετρία **δηλώνεται** αντί να «διορθωθεί» σιωπηλά. Η μετάβαση σε
JIT elevation είναι **ξεχωριστή δουλειά** — αλλά η ραφή προετοιμάζεται: η bypass
απόφαση παύει να είναι σκόρπιο `!isSuperAdmin &&` και γίνεται ονομασμένη έννοια,
ώστε το JIT να μπει σε **ένα** σημείο αντί για 47.

### 7ter.4 Αρχιτεκτονική: PEP/PDP, όχι «ένας φύλακας»

> **OWASP Multi-Tenant**: *«Implement authorization checks at the data access
> layer, not just API layer»* — **layered**.
> **PDP/PEP**: κάθε υπηρεσία είναι **PEP** (εφαρμόζει)· η πολιτική ζει σε **PDP**
> (αποφασίζει)· το **embedded PDP** (in-memory) αποφεύγει το network hop.

Αυτό **είναι** ήδη το σχήμα της Φάσης Β: `tenant-ownership.ts` = PDP, route = PEP.
Το `requireProjectInTenant` **δεν** ταιριάζει επειδή είναι PDP+PEP+**PIP** μαζί
(κάνει το ίδιο το read) ενώ τα 45 αρχεία έχουν **ήδη διαβάσει** — θα έκανε δεύτερο
`get()`. ⇒ **λεπτές κλήσεις PEP + ανά-domain adapter** όπου το σχήμα
επαναλαμβάνεται πανομοιότυπα· το CHECK 3.28 **επιβάλλει** τον adapter εκεί που
υπάρχει επανάληψη και αφήνει ήσυχα τα ιδιόμορφα.

### 7ter.5 Δύο σημεία που **δεν** αντικαθίστανται 1-προς-1

- `messages/delete/route.ts` — **bulk**, απαντά `200` με
  `errors[{reason:'belongs to different company'}]`: per-item soft-fail, όχι throw.
- `rfq-service.getRfq` — καλείται **και** από public vendor portal (HMAC token)
  όπου **δεν υπάρχει `ctx.globalRole`** ⇒ σκέτο `ownedOrNull`, χωρίς
  `concealCrossTenant` (δεν υπάρχει ρόλος να ρωτηθεί).

## 7quater. Φάση Δ — το στρώμα του πράκτορα ΤΝ **DONE** (2026-07-31)

Τα 5 σημεία του `services/ai-pipeline/tools/handlers/**` μεταναστεύθηκαν πρώτα,
γιατί εκεί το μαντείο ύπαρξης δεν ήταν θεωρητικό: **δύο handlers έλεγαν αυτολεξεί
την αλήθεια στο μοντέλο**.

| Handler | Τι έφτανε στο μοντέλο **πριν** |
|---|---|
| `document-reader` | `Access denied: file belongs to a different company.` |
| `file-lifecycle` | `Access denied: file belongs to another company.` |
| `banking` | `Access denied` — **διακριτό** από το «Contact not found» |
| `relationship` | `Access denied — source contact.` |
| `firestore` | `{success:false}` ενώ το γνήσιο κενό είναι `{success:true,data:null}` |

**Νέο**: `services/ai-pipeline/tools/tool-tenant-guard.ts` — `resolveOwnedToolDoc`,
διακριτή ένωση ώστε ο καλών **να μην μπορεί** να ξεχάσει την άρνηση (το `data` δεν
υπάρχει στον αρνητικό κλάδο). Ένα `notFound` callback εξυπηρετεί **και** «δεν
υπάρχει» **και** «ανήκει αλλού» (§7.1).

🔴 **Εδώ η σιωπή δεν είναι επιλογή, είναι το μόνο σωστό**: το `AgenticContext`
φέρει `companyId` + `isAdmin` — και το `isAdmin` είναι ρόλος **εντός** εταιρείας,
**όχι** ο καθολικός bypass. Δεν υπάρχει ρόλος να ρωτηθεί ⇒ ο κλάδος `reveal` δεν
έχει νόημα σε αυτό το στρώμα. Αν ποτέ το `AgenticContext` αποκτήσει `globalRole`,
**αυτό** είναι το ένα σημείο που θα το ρωτήσει, όχι πέντε handlers.

🔴 **Το `firestore-handler` ήταν σπασμένο στο ΣΧΗΜΑ, όχι στο κείμενο.** Το κείμενο
έλεγε ήδη «Document not found» — αλλά το γνήσιο κενό απαντούσε
`{success:true,data:null,count:0}` και το ξένο `{success:false,…}`. **Αρκούσε το
`success` flag** για να ξεχωρίσει τα δύο, χωρίς να διαβαστεί λέξη. ⇒ **Η
μεταμφίεση κρίνεται στο ολόκληρο σχήμα της απόκρισης, όχι στο μήνυμα.**

🔴 **Η σουίτα τεκμηρίωνε το ίδιο το σφάλμα, πράσινη.** Δύο tests στέκονταν
δίπλα-δίπλα: το ένα απαιτούσε `success:true` για «δεν υπάρχει», το άλλο
`success:false` για «ξένο». Ξαναγράφτηκε ώστε να ελέγχει **ταυτότητα** (`toEqual`
μεταξύ των δύο κλάδων) — που είναι το πραγματικό συμβόλαιο.

🐛 **Κενό ασφαλείας που έκλεισε στην πορεία**: το `relationship-handler` έλεγχε
**μόνο την πηγή**. Ο πράκτορας μπορούσε να συνδέσει δική του επαφή με **ξένη**,
και η επιτυχία επιβεβαίωνε ότι το ξένο id υπάρχει. **Η σχέση αγγίζει δύο έγγραφα,
άρα ρωτάει δύο φορές.** ⚠️ Η αφαίρεση του νέου φύλακα άφηνε **12/12 πράσινα** —
γράφτηκαν 4 tests που τη σκοτώνουν.

⚠️ **ΑΛΛΑΓΗ ΣΥΜΠΕΡΙΦΟΡΑΣ (εγκεκριμένη)**: `banking` και `relationship` έγραφαν
`data?.companyId && data.companyId !== ctx.companyId` — άφηναν να περάσει έγγραφο
**χωρίς** `companyId`. Ο SSoT ρωτά `isPayloadOwnedByCompany` ⇒ **έγγραφο χωρίς
tenant δεν ανήκει σε κανέναν** (§4).

### 7quater.1 Boy Scout: ο **εκτελεστής ανάγνωσης** του πράκτορα

Το CHECK 3.28 ανέδειξε **5 προϋπάρχοντες κλώνους** στα ίδια αρχεία (μετρημένους
**ήδη στο HEAD**, άρα «χωριστά commits δεν τα λύνουν»). Καθαρίστηκαν όλοι:

| Κλώνος | Λύση |
|---|---|
| `nullableString` ×2 handlers | → `executor-shared` (κενό ≡ απόν· αλλιώς άδειο πεδίο **σβήνει** τιμή) |
| `accountId` boilerplate ×2 | → `requireAccountId` |
| ο βρόχος «filters→where→orderBy→limit» ×4 | → **νέο** `handlers/firestore-query-plan.ts` |
| η αλυσίδα «επιτρεπτή συλλογή → RBAC → tenant scope» ×2 | → `planScopedRead` |
| το άνοιγμα των δύο read paths | → **`withScopedRead`** (ο εκτελεστής) |

🔴 **Η παγίδα που πληρώθηκε στην εξαγωγή — μην την «απλοποιήσεις» πίσω:** το
τελευταίο καταφύγιο του fallback έγραφε **σκληρά** `where('companyId','==',…)`,
αγνοώντας τον operator. **Δεν ήταν αμέλεια**: το `enforceCompanyScope`, όταν βρει
**υπάρχον** φίλτρο `companyId`, αντικαθιστά **μόνο την τιμή** (`{...f, value}`) και
**κρατά τον operator που έστειλε το μοντέλο** — και το `mapOperator` δέχεται `!=`
και `not-in`. Αφελής χρήση του κοινού βρόχου θα μετέτρεπε το καταφύγιο σε **«όλες
οι ΑΛΛΕΣ εταιρείες»**. Καρφώθηκε με `tenantEqualityFilter` + 4 tests
(`it.each(['!=','not-in','in','>='])`).

Ο **`withScopedRead`** υπάρχει για τον ίδιο λόγο με τον `_domain-route.ts` της
Φάσης Β (§7.8): κάνει το «διάβασε χωρίς tenant scope» **μη εκφράσιμο** — δεν
υπάρχει μονοπάτι προς το `db` που να μην έχει περάσει από την αλυσίδα.

**Επαλήθευση**: **1220/1220** σε 76 suites (`npm run test:ai-pipeline:all`, N.10)·
**10/10 μεταλλάξεις** (σκέτο `===`· φύλακας που παύει να ρωτά· απόκλιση
γνήσιου/μεταμφιεσμένου· αφαίρεση φύλακα πηγής· αφαίρεση φύλακα στόχου· καταφύγιο
που σέβεται τον operator· tenant που χάνεται στο τελευταίο attempt· tenant scope
εκτός αλυσίδας· αντιστροφή σειράς attempts· εκτελεστής που παρακάμπτει)·
**N.18 καθαρό**· N.7.1 όλα τα αρχεία <500 γρ.
