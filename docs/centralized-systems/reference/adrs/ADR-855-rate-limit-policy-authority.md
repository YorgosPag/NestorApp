## 1. Η αφορμή, και γιατί δεν την έψαχνε κανείς

Η **Φ4 του ADR-853** ζήτησε δύο απλά πράγματα: `withSensitiveRateLimit` για τη δημιουργία
πρόσκλησης, `withHeavyRateLimit` για την αποδοχή. Ο έλεγχος του τι **κάνουν** αυτά τα δύο
περιτυλίγματα έδειξε ότι **δεν κάνουν τίποτα διαφορετικό μεταξύ τους**.

```ts
// src/lib/middleware/with-rate-limit.ts
export interface WithRateLimitOptions {
  /** Override the auto-detected category */
  category?: RateLimitCategory;          // ← γρ. 74: δηλώνεται
  getKey?: (request: NextRequest) => string | null;
  skip?: (request: NextRequest) => boolean;
}

export function withRateLimit(handler, options = {}) {
  // …
  const identifier = options.getKey?.(request) ?? extractSecureIdentifier(request);  // ← τιμάται
  result = await checkRateLimit(identifier, endpointPath);                            // ← το category ΔΕΝ περνά
}
```

```ts
// src/lib/middleware/rate-limiter.ts:101
export async function checkRateLimit(identifier, endpointPath) {
  const category = getCategory(endpointPath);   // ← Η ΜΟΝΗ πηγή κατηγορίας
  const limit = getLimit(category);
  // …
}
```

**Το `options.category` δεν διαβάζεται πουθενά.** Εμφανίζεται τρεις φορές στο αρχείο: στη
δήλωση του τύπου (γρ. 74), σε ένα σχόλιο παραδείγματος (γρ. 171) και στις **επτά** κλήσεις των
προ-ρυθμισμένων περιτυλιγμάτων (γρ. 261-309). Στο σώμα της συνάρτησης, **καμία**.

🔴 **Και το χειρότερο δεν είναι η παράλειψη — είναι ότι το διπλανό πεδίο ΔΟΥΛΕΥΕΙ.** Στο ίδιο
αντικείμενο επιλογών, το `getKey` τιμάται κανονικά (γρ. 197). Δύο διαδρομές τηλεμετρίας
γράφουν **και τα δύο μαζί**:

```ts
// src/app/api/telemetry/bim-performance/erase/route.ts:121
export const POST = withRateLimit(handlePost, {
  category: 'HEAVY',                    // ← αγνοείται σιωπηλά
  getKey: (req) => { /* … */ },         // ← δουλεύει
});
```

Ο συγγραφέας βλέπει το ένα μισό της δήλωσής του να λειτουργεί και συμπεραίνει ότι λειτουργεί
και το άλλο. **Δεν υπάρχει σήμα** — καμία προειδοποίηση, κανένα σφάλμα, καμία δοκιμή.

## 2. Τι υπόσχεται η τεκμηρίωση, και τι συμβαίνει

| Πηγή | Η υπόσχεση | Η μέτρηση |
|---|---|---|
| **ADR-068 §3** γρ. 150-151 | `withSensitiveRateLimit` → **20** req/min · `withHeavyRateLimit` → **10** | και τα δύο → **60** |
| **ADR-068 §10** γρ. 864 | *«Every new route MUST use one of the 6 rate limit wrappers»* | ο wrapper **δεν αλλάζει τίποτα** |
| **PR-1C** γρ. 203-207 | *«### Override Auto-Detection — Force SENSITIVE category regardless of path»* | το `category` **δεν διαβάζεται ποτέ** |
| **ADR-844** γρ. 613 | *«`withHeavyRateLimit` της διαδρομής (10/λεπτό ανά IP), που **δεν** παρακάμπτεται»* | είναι **60** |
| **ADR-170** (QR) | `Rate: withHeavyRateLimit (10 req/min — anti-brute-force)` | είναι **60** |

⚠️ **Τέσσερα έγγραφα λένε το ίδιο ψέμα, και κανένα δεν το είπε από κακή πίστη**: όλα
περιγράφουν τη **δηλωμένη πρόθεση** της αρχιτεκτονικής. Ο κώδικας απλώς δεν τη συνέδεσε ποτέ.

Ο **μόνος** πραγματικός φρουρός είναι ο πίνακας `ENDPOINT_CATEGORY_MAPPINGS` — **εννέα**
γραμμές προθεμάτων, για **449** διαδρομές.

## 3. Η μέτρηση — 449 διαδρομές, μία προς μία

Μετρήθηκε 2026-09-12 αντιπαραβάλλοντας, για κάθε `route.ts`, τι **δηλώνει** ο wrapper του με
τι **επιβάλλει** σήμερα ο πίνακας:

```
ΣΥΝΟΛΟ route.ts        : 449
χωρίς κανέναν wrapper  : 152
ΣΥΜΦΩΝΟΥΝ              : 208
ΔΙΑΦΩΝΟΥΝ              :  89
```

### 3.0 🔴 Το «152 αδήλωτες» ήταν **λάθος κατά 75** — και γι' αυτό μετρήθηκε δεύτερη φορά

Η πρώτη μέτρηση ρώτησε *«έχει αυτό το αρχείο wrapper;»*. Λάθος ερώτηση: **75** διαδρομές
δηλώνουν βαθμίδα **έμμεσα**, μέσα από εργοστάσιο που τυλίγει το ίδιο:

```
ΑΜΕΣΗ δήλωση (wrapper)     : 297
ΕΜΜΕΣΗ δήλωση (εργοστάσιο) :  75   ← 40 defineRoute · 14 createScanCronRoute ·
ΣΙΩΠΗΛΕΣ (καμία δήλωση)    :  77      6 createPublicTokenRouteExport · 5 createShowcaseEmailRoute ·
                                      4 createMigrationRoute · 3 createMetaWebhookRoute ·
                                      2 createQueueCronRoute · 1 adminDirectOperationWrite
```

⚠️ **Με το αφελές κριτήριο, η πύλη του Α5 θα γεννιόταν με 75/152 = 49% ψευδώς θετικά** —
πενταπλάσια του πήχη <10% που αυτό το repo απαιτεί για μπλοκάρουσα πύλη (3.68 · 3.61 · 3.76).
Ο πληθυσμός του ratchet είναι **77**, όχι 152, και κάθε όνομα εργοστασίου επαληθεύτηκε
**εκτελώντας grep στην πηγή του**, ποτέ μαντεμένο.

### 3.1 Η βλάβη είναι **αμφίδρομη** — και αυτό ανατρέπει την πρώτη υπόθεση

| # | Δηλώνει | Επιβάλλεται | Κατεύθυνση |
|---|---|---|---|
| 41 | SENSITIVE (20) | STANDARD (60) | **×3 πιο χαλαρά** |
| 21 | HEAVY (10) | STANDARD 60 / SENSITIVE 20 | **έως ×6 πιο χαλαρά** |
| 13 | STANDARD (60) | HEAVY (10) | **×6 πιο ΣΦΙΧΤΑ** |
| 6 | STANDARD (60) | SENSITIVE (20) | **×3 πιο σφιχτά** |
| 5 | HIGH (100) | STANDARD (60) | **πιο σφιχτά** |
| 2 | TELEGRAM (15) | SENSITIVE 20 / WEBHOOK 30 | χαλαρότερα |
| 1 | STANDARD (60) | HIGH (100) | χαλαρότερα |

Η πρώτη ανάγνωση του ελαττώματος ήταν *«όλα τρέχουν στα 60»*. **Λάθος, μετρημένα**: **24**
διαδρομές τρέχουν **αυστηρότερα** από όσο ζήτησαν. Και οι δεκατρείς πρώτες είναι όλες οι
`/api/reports/*` — που πνίγονται στα **10/min** επειδή ο πίνακας έχει το πρόθεμα `/api/reports`
ενώ οι ίδιες δήλωσαν `withStandardRateLimit`. Μαζί τους έξι **read-only** οθόνες διαχειριστή
(`/api/admin/backup/list`, `…/backup/status`, `…/environment`, `…/restore/status`,
`…/bim-diagnostics/*`) και πέντε λίστες `financial-intelligence` που ζήτησαν 100 και παίρνουν 60.

### 3.2 Οι διαρροές χτυπούν ακριβώς εκεί που το όριο είναι ο **μόνος** φρουρός

Δηλώνουν **HEAVY (10)** και τρέχουν στα **60**:

Δηλώνουν **SENSITIVE (20)** και τρέχουν στα **60** — η επιφάνεια ταυτότητας, ολόκληρη:


🔴 Το **ADR-068 §6 «Category Assignment Logic»** δηλώνει ρητά *«SENSITIVE: `/api/admin/*`,

Ομοίως το `/api/*/export` του §6 **δεν εκφράζεται** με `startsWith`: το
`/api/procurement/spend-analytics/export` δεν αρχίζει από `/api/export`.

## 4. 🔴 Δεύτερο εύρημα: η δηλωμένη μετρίαση του ADR-068 **δεν υπάρχει**

**ADR-068 §4 «Risk Mitigation»**:

| Risk | Mitigation | Status |
|---|---|---|
| **Upstash Redis Down** | Fallback to in-memory store (graceful degradation) | ✅ Implemented |

Ο `getRateLimitStore()` επιλέγει store **μία φορά**, ως singleton, στην πρώτη κλήση. Αν το
Upstash πέσει **αργότερα**, δεν υπάρχει καμία διαδρομή προς τη μνήμη: ο
`UpstashRateLimitStore.check` πιάνει το σφάλμα και επιστρέφει

```ts
// rate-limit-store.ts:289-299
// Fail open in case of error (allow the request)
return { allowed: true, current: 0, limit, resetMs: windowMs };
```

Δηλαδή **fail-open, καθολικά** — συμπεριλαμβανομένου του `/api/first-contacts/guest/confirm`
που φυλά εξαψήφιο κωδικό, και του `/api/auth/password-reset`.

Το ADR-068 **δεν συζητά** fail-open πουθενά (επαληθεύτηκε με σάρωση του §7 Security Analysis).

⚠️ Και σε **serverless** ένα `Map` στη μνήμη της διεργασίας δεν εγγυάται τίποτα: κάθε ψυχρή
εκκίνηση το μηδενίζει, κάθε παράλληλο instance έχει δικό του.

### Τέταρτο: όριο δηλωμένο και **ανενεργό**

`telegram/bot-security.ts:37` → `MAX_QUERIES_PER_MINUTE: 15`. Μετρημένο: **μία** εμφάνιση σε
όλο το δέντρο — τη δήλωσή του. Κανείς δεν το επιβάλλει. *(Το Telegram έχει **σωστό** όριο: το
`process-message.ts:77` καλεί κανονικά το SSoT.)*

### Πέμπτο: ένα **πέμπτο κανάλι** δήλωσης — και είναι το **καλό** παράδειγμα

`createPublicTokenRouteExport(route, 'standard' | 'none')` (`showcase-core`): το `'none'`
παρακάμπτει **εντελώς** τον limiter (γρ. 61-63). **Έξι** διαδρομές — 4 δημόσιες ανώνυμες
payload με `'none'`, 2 PDF proxies με `'standard'`.

🏆 **ΚΑΙ ΕΔΩ ΤΟ REPO ΕΧΕΙ ΗΔΗ ΛΥΣΕΙ ΤΟ ΕΡΩΤΗΜΑ ΤΟΥ Α5**, με γραμμένο το σκεπτικό
(`create-token-route-export.ts:20-23`):

> *«Making the parameter **required** means every route file now **states** which side it is
> on, so the gap is **visible in review** instead of implied by an absent wrapper.»*

…και με **άγκυρα** που το επιβάλλει (`public-showcase-surface.test.ts:355`) συν **tripwire**
που καρφώνει την τρέχουσα εικόνα *(«Not an endorsement — a tripwire»)*.

⇒ Η πύλη του **Α5 δεν είναι νέα ιδέα: είναι η γενίκευση ενός προτύπου που αυτό το δέντρο
έχει ήδη γράψει, δοκιμάσει και τεκμηριώσει** σε έξι διαδρομές. Επεκτείνεται στις 449.

## 5. Η έρευνα — τι κάνουν οι μεγάλοι

### 5.1 Δήλωση πολιτικής: **δίπλα στη διαδρομή**, όχι σε κεντρικό πίνακα προθεμάτων

**Envoy Gateway** (`RateLimitPolicy` ανά `HTTPRoute`), **NGINX Gateway Fabric**
(`RateLimitPolicy` API), **API7/APISIX** (policy ανά route/consumer): η ομόφωνη σύγχρονη
πρακτική είναι **declarative policy προσαρτημένη στη διαδρομή**. Το κεντρικό ταίριασμα
προθεμάτων ζει στο **gateway**, ως χονδρικό ταβάνι — ποτέ ως η μόνη αυθεντία.

🔑 **Και το ίδιο το ADR-068 το είχε ήδη σχεδιάσει σωστά**: οι επτά wrappers **είναι** η
δήλωση δίπλα στη διαδρομή. Απλώς δεν συνδέθηκαν ποτέ με τη μηχανή.

⚠️ **Η «Alternative 1» που το ADR-068 §5 απέρριψε ΔΕΝ είναι αυτό.** Εκείνη ήταν *«κάθε
διαδρομή γράφει δική της λογική Redis inline»* — 910 γραμμές αντιγραφής, χωρίς sliding window,
χωρίς απομόνωση μισθωτή. Η απόρριψή της μένει **ακέραιη**: εδώ υπάρχει **μία** μηχανή και η
διαδρομή δηλώνει μόνο **ποια βαθμίδα** θέλει.

### 5.2 Fail-open vs fail-closed: **ανά διαδρομή**, ποτέ καθολικά

Η βιομηχανία συμφωνεί και στις δύο κατευθύνσεις: *fail-open* για γενικά API (μια βλάβη του
limiter δεν πρέπει να γίνεται βλάβη του API), αλλά **fail-closed για ό,τι φυλά διαπιστευτήρια
ή χρήματα** — *«Authentication MUST fail closed — allowing a request you couldn't authorize is
a security bypass»*. Η οδηγία για Next.js App Router το λέει κατά λέξη: *«choose per-route fail
behavior: fail closed on authentication and on anything that spends money, fail open on reads»*.

### 5.3 Κεφαλίδες: το IETF πρότυπο, που **κανείς από τους μεγάλους δεν στέλνει ακόμη**

`draft-ietf-httpapi-ratelimit-headers-11` (23 Μαΐου 2026, **Standards Track**) ορίζει δύο
Structured Fields (RFC 9651):

```http
RateLimit-Policy: "default";q=20;w=60
RateLimit: "default";r=17;t=43
```

Το ίδιο το draft δηλώνει ότι τα `X-RateLimit-*` έχουν *«significant interoperability problems
due to inconsistent semantics across implementations»*. **GitHub και Stripe στέλνουν ακόμη τα
παλιά.** Εμείς στέλνουμε επίσης `X-RateLimit-*` (`rate-limiter.ts:211-220`).

## 7. Οι αποφάσεις

### Α1 — Η **δήλωση** της διαδρομής είναι η αυθεντία· ο πίνακας γίνεται **εφεδρεία**

```ts
checkRateLimit(identifier, endpointPath, options.category)
//                                        ^^^^^^^^^^^^^^^^ νέα, προαιρετική
```

- Δηλωμένη βαθμίδα ⇒ **αυτή** ισχύει.
- **Καμία** δήλωση ⇒ ο πίνακας προθεμάτων, όπως σήμερα (οι 152 αδήλωτες δεν αλλάζουν).

⛔ **ΔΕΝ διαγράφεται ο πίνακας.** Καλύπτει τις αδήλωτες και εκφράζει χονδρικές πολιτικές
(`/api/admin/*`). Γίνεται **δεύτερη γραμμή**, όχι πρώτη.

### Α2 — Ο πίνακας ευθυγραμμίζεται με τη **δηλωμένη πρόθεση** του ADR-068 §6

Προστίθενται τα δηλωμένα-και-απόντα: `/api/auth`, `/api/oauth`, `/api/pricing`, `/api/setup`.
⚠️ **Μετά** το Α1, ώστε η αλλαγή να είναι μετρήσιμη χωριστά.

### Α3 — Fail-closed **ανά βαθμίδα**, δηλωμένο στον κατάλογο

Ο `RATE_LIMIT_CATEGORIES` παύει να είναι `Record<string, number>` και γίνεται πίνακας
**πολιτικής**: όριο **και** συμπεριφορά σε βλάβη του store **και** γραμμένος λόγος.

- `SENSITIVE` · `HEAVY` (δημόσιες πόρτες, brute-force) ⇒ **fail-closed** (503).
- `STANDARD` · `HIGH` · `ASSET` (αναγνώσεις) ⇒ **fail-open**, όπως σήμερα.

🔑 Η αλλαγή τύπου **δεν** είναι καλλωπισμός: σήμερα ένας αριθμός δεν έχει πού να κουβαλήσει
την απόφαση, οπότε η απόφαση δεν υπάρχει.

### Α4 — Κεφαλίδες IETF **δίπλα** στις υπάρχουσες, ποτέ αντί για αυτές

Οι `X-RateLimit-*` μένουν (τις διαβάζει ο `enterprise-api-client`). Προστίθενται
`RateLimit-Policy` και `RateLimit`.

### Α5 — **CHECK 3.78**: κάθε διαδρομή δηλώνει, και η δήλωση συμφωνεί με την επιβολή

Δύο κριτήρια, **ποτέ ένα με «ή»** (μάθημα CHECK 3.41):

| | Ερώτημα | Μηχανισμός |
|---|---|---|
| **Κ1** | *«δηλώνει αυτή η διαδρομή βαθμίδα;»* | 🔴 RATCHET (152 αδήλωτες σήμερα — εκστρατεία προς το μηδέν) |
| **Κ2** | *«συμφωνεί η δήλωση με ό,τι θα επιβληθεί;»* | 🔴 RATCHET κατά **ταυτότητα** (89 σήμερα· «89 → 89» με ανταλλαγή **μπλοκάρει**) |

⚠️ **Ratchet και όχι zero-tolerance**, μετρημένα: 152 + 89 = **241** ζωντανές ⇒ zero-tol θα
ήταν μονίμως κόκκινο ⇒ `SKIP_` ⇒ **διακοσμητική πύλη** — η παγίδα που το CHECK 3.39 δοκίμασε
και απέρριψε γραπτώς.

## 8. 🔶 Δηλωμένα όρια — γραμμένα αντί να κρυφτούν

1. **Η διόρθωση του Α1 σφίγγει 65 διαδρομές στην ίδια στιγμή.** Είναι το **ζητούμενο** (οι
   διαδρομές παίρνουν επιτέλους ό,τι ζήτησαν), αλλά είναι και **αλλαγή συμπεριφοράς
   παραγωγής**. Γι' αυτό η Φ1 μετρά **πριν και μετά**, ανά διαδρομή, και ο κατάλογος των 65
   μπαίνει στο changelog ονομαστικά.
2. **Δεν αγγίζουμε τις 152 αδήλωτες σε αυτό το ADR.** Το ratchet του Κ1 τις καταγράφει· η
   συμπλήρωσή τους είναι Boy Scout δουλειά, όχι μαζική αλλαγή ορίων χωρίς μέτρηση ανά πόρο.
3. **Το fail-closed του Α3 μπορεί να κόψει νόμιμη κίνηση σε βλάβη του Upstash.** Είναι
   **σκόπιμο** για τις δύο βαθμίδες που φυλάνε διαπιστευτήρια, και **μόνο** γι' αυτές.
4. **Ο πίνακας παραμένει `startsWith`.** Μοτίβα τύπου `/api/*/export` εξακολουθούν να μην
   εκφράζονται· η θεραπεία τους είναι η **δήλωση** στη διαδρομή (Α1), όχι πλουσιότερη γραμματική
   ταιριάσματος — που θα ήταν δεύτερη μηχανή για ερώτημα που έχει ήδη απάντηση.

## 11. Τι **απορρίφθηκε**, με λόγο

| Απορρίφθηκε | Γιατί |
|---|---|
| **Διαγραφή του πίνακα** — «η δήλωση αρκεί» | 152 διαδρομές δεν δηλώνουν τίποτα· θα έπεφταν όλες σε μία προεπιλογή, συμπεριλαμβανομένων 13 κάτω από `/api/admin` |
| **Σιωπηλή αφαίρεση του `options.category`** από τον τύπο | Θα «έλυνε» την αντίφαση σβήνοντας την **πρόθεση**, και θα άφηνε τα 5 ADR να λένε ψέματα |
| **Zero-tolerance στην πύλη 3.78** | 241 ζωντανές παραβιάσεις ⇒ μονίμως κόκκινο ⇒ `SKIP_` (CHECK 3.39 το απέρριψε γραπτώς) |
| **Αντικατάσταση των `X-RateLimit-*`** από τις IETF | ⚠️ **Ο πρώτος λόγος που γράφτηκε εδώ ήταν ΨΕΥΔΗΣ και διορθώθηκε**: υποτέθηκε ότι «ο `enterprise-api-client` τις διαβάζει». **Μετρήθηκε: δεν τις διαβάζει κανείς** — το grep για `429\|Retry-After\|retryAfter` σε εκείνο το αρχείο δίνει **μηδέν**, και ο μόνος ειδικός χειρισμός status είναι το `401` (καθάρισμα token). Ο **πραγματικός** λόγος διατήρησης: είναι **δημόσιο συμβόλαιο σύρματος** — το γράφουν **δύο** σημεία (`rate-limiter.ts:215-218` και, χειρόγραφα, `property-share/route.ts:82`) και το διαβάζουν εργαλεία/πελάτες εκτός αυτού του δέντρου. Αφαίρεση = σπάσιμο χωρίς μετρημένο κέρδος· **προσθήκη** των IETF δίπλα τους κοστίζει δύο κεφαλίδες |
| **Πλουσιότερο ταίριασμα προθεμάτων** (`/api/*/export`) | Δεύτερη μηχανή για ερώτημα που απαντά η δήλωση (Α1) — ADR-749 |
| **Καθολικό fail-closed** | Βλάβη του Upstash θα γινόταν βλάβη **όλου** του API — η βιομηχανία το αποκλείει ομόφωνα για αναγνώσεις |
