# ADR-747 — Η πύλη που έλειπε ανάμεσα σε δύο πύλες: tenant scope με AST (CHECK 3.35)

**Κατάσταση:** Ενεργό
**Ημερομηνία:** 2026-08-01
**Συγγραφέας:** Claude (Opus 5) + Γιώργος Παγώνης
**Κατηγορία:** Security / Multi-tenancy / Static Analysis / Pre-commit Gates
**Σχετικά:** **ADR-745 §9.5** (το σφάλμα που το γέννησε) · ADR-702 (`scopeQueryToTenant`) ·
ADR-742 (`scopeQueryToCompany`, «ένα gate δεν γεννιέται κόκκινο») · ADR-294 (SSoT ratchet) ·
ADR-584 (jscpd — το ίδιο σχήμα «ο έλεγχος κοιτά λάθος πράγμα») · ADR-245B (`FIELDS.*`) ·
CHECK 3.10 (`check-firestore-companyid.sh`) · CHECK 3.15 (`check-firestore-index-coverage.js`)

---

## Summary

Δύο πύλες φύλαγαν το tenant isolation των Firestore queries. **Η μία παρέπεμπε ρητά στην
άλλη για ένα σκέλος· η άλλη ήταν δομικά τυφλή σε ακριβώς αυτό το σκέλος.** Το κενό έπεφτε
ανάμεσά τους και **καμία δεν το διεκδικούσε** — γι' αυτό το `getAllContacts` έστελνε
αφιλτράριστη λίστα επαφών επί μήνες ενώ η baseline του CHECK 3.10 έγραφε
«**0 violations / 0 files — fully cleaned**».

Το ADR-747 κλείνει το κενό με **έναν** σαρωτή AST που απαντά **και τους δύο** κανόνες
(client SDK spread· Admin SDK αλυσίδα), γεννημένο **πράσινο** ως ratchet ανά αρχείο.

## 1. Το εύρημα, με τα λόγια των ίδιων των αρχείων

### 1.1 Η παραπομπή

`scripts/check-firestore-index-coverage.js`, γρ. 38-44:

```
Scope / limitations (v1):
  - Only analyses `firestoreQueryService.subscribe` and `.getAll`.
    Direct `query()` + `getDocs()` usage is covered by CHECK 3.10
    (firestore companyId) and its future follow-up.
```

### 1.2 Η τυφλότητα

`scripts/check-firestore-companyid.sh`, γρ. 52-61:

```bash
# Find query() calls and check if they have companyId in the next 12 lines
block=$(sed -n "${lineno},$((lineno+11))p" "$file")
if echo "$block" | grep -q "where(" && ! echo "$block" | grep -q "companyId"; then
```

**12 γραμμές προς τα κάτω**, και μαρκάρισμα **μόνο** αν το block περιέχει `where(`.
Στο κυρίαρχο idiom του έργου:

```ts
const constraints: QueryConstraint[] = [];
if (options?.type) constraints.push(where('type', '==', options.type));   // ← 16 γραμμές ΠΑΝΩ
// …
return query(getCol(CONTACTS_COLLECTION, contactConverter), ...constraints);  // ← ΤΕΛΕΥΤΑΙΑ γραμμή
```

το block **δεν περιέχει κανένα `where(`** ⇒ `grep -q "where("` αποτυγχάνει ⇒
**μηδέν παραβιάσεις, πάντα**. Ο έλεγχος βλέπει **μόνο** το inline `query(col, where(…))`.

> 🔴 **Τέταρτη εμφάνιση του «`0` = κανείς δεν κοίταξε»** — μετά το i18n (N.11), το
> `ssot-discover` (N.12) και το ίδιο το CHECK 3.15. **Το `0` δεν είναι δείκτης υγείας.**

### 1.3 Ο δίδυμος κανόνας

Το ίδιο σφάλμα, άλλο σχήμα κειμένου: το Admin SDK γράφει `.collection(X).where(…)` —
**σχήμα που το CHECK 3.10 δεν κοιτά καθόλου**. Τρία σημεία στο `contact_links` έμειναν
ασκόπιστα επί μήνες, **ένα εξ αυτών ΕΓΓΡΑΦΗ** (διορθώθηκαν στο ADR-745 §9.3).

> **Γι' αυτό λύνονται ΜΑΖΙ, με ΕΝΑΝ σαρωτή:** και οι δύο είναι «η πύλη κοιτά **σχήμα
> κειμένου**, ο κώδικας γράφτηκε σε **άλλο σχήμα**». Η θεραπεία είναι κοινή:
> **AST αντί για grep γραμμών — ακολούθησε το ΟΝΟΜΑ.**

## 2. Τρεις μορφές του ίδιου σχήματος

| # | Μορφή | Ποια πύλη την έβλεπε |
|---|---|---|
| 1 | `const c=[]; c.push(where(…)); query(col, ...c)` | **καμία** (3.10 τυφλό) |
| 2 | `db.collection(X).where(…)` | **καμία** (άλλο σχήμα) |
| 3 | `let q=db.collection(X)…; if (!isSuperAdmin) q=q.where(COMPANY_ID,…)` | **καμία** |

⚠️ Η **(3) δεν ήταν στην αρχική προδιαγραφή** — βρέθηκε **μετρώντας**. Είναι νόμιμος
κώδικας που ο πρώτος σαρωτής μετρούσε παραβίαση. Χωρίς αυτήν η πύλη θα γεννιόταν θορυβώδης.

## 3. Η μέτρηση **πριν** τη σχεδίαση — και τι αποκάλυψε για τον ίδιο τον σαρωτή

Η απόφαση «ratchet ή zero-tolerance» δεν λήφθηκε θεωρητικά. Έγινε απογραφή σε **11.062**
αρχεία, και **τρεις φορές το εργαλείο διορθώθηκε επειδή έλεγε ψέματα**:

| # | Τι έλειπε από τον σαρωτή | Επίπτωση (μετρημένη) |
|---|---|---|
| 1 | Τοπικά ψευδώνυμα `const CONTACTS_COLLECTION = COLLECTIONS.CONTACTS` | **65%** των client sites έβγαινε «άγνωστη συλλογή» και **πετιόταν σιωπηλά** — μαζί με το ίδιο το ιστορικό σφάλμα |
| 2 | Σταθερές πεδίων `FIELDS.COMPANY_ID` (ADR-245B, **73 χρήσεις**) | **61%** ψευδώς θετικά στον Admin SDK (199 → 145) |
| 3 | Επανανάθεση `q = q.where(COMPANY_ID, …)` | 6 ακόμη ψευδώς θετικά σε **νόμιμο** κώδικα (145 → 139) |

> 🔴 **Το (1) είναι το σημαντικότερο μάθημα του ADR.** Η πρώτη εκδοχή είχε κατηγόρημα
> `violation: … && !!coll` — δηλαδή **ό,τι δεν αναγνώριζε, εξαφανιζόταν**. Ο σαρωτής που
> γράφτηκε για να λύσει το «0 = κανείς δεν κοίταξε» **το αναπαρήγαγε στον εαυτό του** και
> θα ανέφερε «0 παραβιάσεις» για το αρχείο που **είχε** τη διαρροή.
>
> Θεραπεία, τώρα δομική: **πέντε ρητές καταστάσεις** — `violation` · `ok` · `unanalyzable`
> · `exempt` · `not-tenant-scoped`. **Καμία σιωπηλή απόρριψη.** Ένα εύρημα που δεν
> κατατάσσεται είναι **δεδομένο που χάθηκε**, όχι «καθαρό».

### 3.1 Και ένα τέταρτο, στην ίδια την πύλη

Ο σαρωτής αρχικά δεχόταν κριτήριο **επιπέδου αρχείου** («το αρχείο αναφέρει
`resolveEffectiveCompanyId` ⇒ εντάξει»). Αυτό είναι **ακριβώς** το σχήμα του ADR-745:
το `contacts-query.service.ts` είχε **έξι** συναρτήσεις, οι **πέντε** περνούσαν από τον
SSoT και **μία όχι**. Το κριτήριο θα έβαφε **πράσινη** τη σπασμένη επειδή οι **γειτόνισσές**
της ήταν σωστές — η πύλη θα **πιστοποιούσε** τη διαρροή.

**Αφαιρέθηκε.** Η μόνη αποδεκτή εγγύηση είναι **ανά σημείο κλήσης**. Regression anchor:
`sibling-masking.ts.fixture` + 2 tests.

## 4. Η απόφαση: ratchet, όχι zero-tolerance

Τελική μέτρηση: **145 παραβιάσεις σε 90 αρχεία** (135 Admin SDK + 10 client).
Χειροκίνητη κατηγοριοποίηση των Admin SDK:

| Κατηγορία | # | Κρίση |
|---|---|---|
| έμμεση εμβέλεια από γονέα (`projectId`, `buildingId`…) | 42 | γκρίζο — δομικά επικίνδυνο, όχι σφάλμα |
| θέλει μάτι | 41 | μεικτό (cron/GDPR/oauth νόμιμα) |
| ai-pipeline internal | 19 | πιθανόν `mode:'none'` που λείπει από το tenant-config |
| admin/migration | 16 | cross-tenant **εκ σχεδιασμού** |
| public capability token | 10 | **νόμιμο** — το token *είναι* η εξουσιοδότηση |
| `__name__` doc-ID batch | 7 | **νόμιμο** — IDs από ήδη-scoped γονέα |
| inbound webhook | 4 | **νόμιμο** — δεν υπάρχει ακόμη μισθωτής |

Ποσοστό ψευδώς θετικών **πολύ πάνω** από τον πήχη **≤10%** που θέτει η Google για
blocking analyzers (Tricorder). Zero-tolerance θα σήμαινε **145 κόκκινα σε καθαρό repo**,
και υπάρχει ρητό προηγούμενο ότι **«ένα gate δεν επιτρέπεται να γεννηθεί κόκκινο»**
(ADR-742, commit `b4ec47e2`).

⇒ **Ratchet ανά αρχείο.** Τα 145 μπαίνουν στη baseline· μπλοκάρονται μόνο **νέα** και
**οπισθοδρομήσεις**.

> 🔴 **Και η baseline λέει ειλικρινά «145», όχι ψεύτικο «0».** Αυτή είναι η ουσία όλου
> του ADR: το `.firestore-companyid-baseline.json` έλεγε «0 — fully cleaned» ενώ η διαρροή
> ήταν ενεργή. Ένα ειλικρινές 145 είναι ασύγκριτα πιο χρήσιμο από ένα ψεύτικο 0.
> Το `_meta.note` της baseline το δηλώνει ρητά: **δεν είναι δείκτης υγείας**.

|---|---|

## 6. Ρητή εξαίρεση — με **υποχρεωτικό** λόγο

```ts
// tenant-scope-exempt: δημόσια αγγελία — το query ΕΙΝΑΙ ο κανόνας
// Το firestore.rules:797 επιτρέπει ανώνυμη ανάγνωση ακριβώς όταν
// commercialStatus in ['for-sale','for-rent','for-sale-and-rent'] …
const q = query(collection(db, COLLECTIONS.PROPERTIES), ...constraints);
```

Ο λόγος είναι **υποχρεωτικός** (`tenant-scope-exempt:` χωρίς κείμενο **δεν** αναγνωρίζεται) —
ίδιο δόγμα με `eslint-disable-next-line <rule> -- reason`.

> 🔴 **Και εδώ η πρώτη εκδοχή τιμωρούσε την τεκμηριωμένη εξαίρεση.** Κοιτούσε **μία**
> γραμμή πάνω από το query· μια σοβαρή αιτιολογία (παραπομπή σε κανόνα rules + ADR + τι
> σπάει) είναι μπλοκ 10 γραμμών ⇒ **δεν αναγνωριζόταν**, ενώ η βιαστική μονόγραμμη ναι.
> Τώρα σαρώνεται **ολόκληρο το συνεχόμενο μπλοκ σχολίων**, σταματώντας στην πρώτη γραμμή
> κώδικα (ώστε η εξαίρεση να ανήκει σε **ένα** σημείο). 2 anchor tests.

## 8. Απόδειξη ότι ο φύλακας φυλάει

**45 tests, όλα πράσινα.** Τρία διακριτά είδη:

1. **Διαφορικό στο πραγματικό ιστορικό σφάλμα.** Fixtures με τον **αυτούσιο** κώδικα του
   `3d1339ce^` και του `3d1339ce`:
   - πριν → **1 violation**, `fields=[isFavorite,type]`, **χωρίς** `companyId`
   - μετά → **0**, και **για τον σωστό λόγο** (`detail: «φιλτράρει σε companyId»`)
   - + αναπαραγωγή του αλγορίθμου του CHECK 3.10 στο ίδιο fixture ⇒ **0 flagged**,
     αποδεικνύοντας την τυφλότητα **εκτελεστικά**, όχι με ισχυρισμό.
2. **Αντι-θόρυβος** — κάθε idiom που μετρήθηκε ότι παρήγαγε ψευδώς θετικά.
3. **Mutation testing — 5/5 σκοτωμένες**, με **δύο** επίπεδα επαλήθευσης:
   - ότι η μετάλλαξη **ταίριαξε** στο αρχείο (`expect(original.includes(find)).toBe(true)`)
   - ότι **έφτασε στη μνήμη**.

> 🔴 **Η δεύτερη άμυνα βρέθηκε επειδή απέτυχε.** Το `delete require.cache[…]` **δεν κάνει
> τίποτα στο Jest** — το Jest έχει **δικό του** module registry. Τέσσερις από τις πέντε
> μεταλλάξεις «περνούσαν» ενώ έτρεχε ο **παλιός** κώδικας: το αρχείο στον δίσκο άλλαζε,
> η συνάρτηση όχι. Θεραπεία: `jest.resetModules()` + `jest.isolateModules()`, **και ένα
> Μ0 meta-test** που βάφει ετικέτα κατάστασης και απαιτεί να τη δει στην έξοδο.
>
> **Χωρίς το Μ0, το «5/5 σκοτωμένες» θα ήταν ψέμα.** Το συμβόλαιο προειδοποιούσε για
> μεταλλάξεις που δεν προσγειώνονται στο **αρχείο**· αυτή δεν προσγειωνόταν στη **μνήμη** —
> μια δεύτερη, ανεξάρτητη εκδοχή του ίδιου κινδύνου.

## 9. Σχέση με το CHECK 3.10

Το CHECK 3.35 καλύπτει **γνησίως περισσότερα** από όσα μπορεί να δει το 3.10 (κάθε inline
`query(col, where(…))` που το 3.10 πιάνει, το πιάνει και ο AST σαρωτής· το αντίστροφο δεν
ισχύει). **Το 3.10 δεν καταργείται σε αυτό το ADR** — μένει ως δεύτερο, χονδροειδές δίχτυ
που δεν εξαρτάται από ανάλυση συλλογής.

**Πρόταση προς τον Γιώργο (δεν εκτελέστηκε):** μόλις το 3.35 τρέξει έναν κύκλο στο CI,
να αφαιρεθεί το 3.10 **μαζί με τη baseline του** — γιατί ένα gate που λέει μονίμως «0»
δεν είναι απλώς άχρηστο, **παράγει ενεργά ψεύτικη ασφάλεια**.

## 10. Τι **δεν** κάνει

- Δεν ακολουθεί constraints **διά μέσου αρχείων** ⇒ `unanalyzable`, **ποτέ** violation.
  Η άγνοια δεν είναι ενοχή (198 τέτοια σημεία σήμερα).
- Δεν κρίνει **πολιτική** (ποιος δικαιούται cross-tenant) — αυτό είναι του `scopeQueryToTenant`
  (ADR-702). Εδώ κρίνεται μόνο αν το φίλτρο **υπάρχει**.
- Δεν αγγίζει `.doc(id)` reads — άλλη ερώτηση, την κρίνουν τα rules.

## 11. Δουλειά Γ — τα 3 «αμέτρητα» αρχεία (ADR-745 handoff §4)

Και τα τρία **μετρήθηκαν** και είναι **νόμιμα** — αλλά τώρα με απόδειξη, όχι υπόθεση:

| Αρχείο | Ετυμηγορία |
|---|---|
| `services/notificationService.ts` | ✅ `mode:'userId'` στο tenant-config, φιλτράρει σε `userId`. Το «δεν αναφέρει companyId» ήταν **σωστό και αναμενόμενο** |
| `services/realtime/hooks/usePublicProperties.ts` | ✅ δημόσια αγγελία· το `LISTED_COMMERCIAL_STATUSES` είναι **byte-ταυτόσημο** με το allowlist του `firestore.rules:797`. **Το query ΕΙΝΑΙ ο κανόνας** ⇒ τεκμηριωμένη εξαίρεση |
| `api/communications/webhooks/telegram/firebase/helpers-lazy.ts` | ✅ δεν είναι query· είναι **wrapper factory** (`collection(path)` γενικού σκοπού). `unanalyzable` = σωστή ετυμηγορία· τα πραγματικά queries ζουν στα call sites |

## 12. Changelog

**(α) 2026-08-01 — γέννηση.** Απογραφή 11.062 αρχείων· τρεις διορθώσεις του σαρωτή πριν
εμπιστευτεί κανείς αριθμό (ψευδώνυμα 65%, `FIELDS` 61%, επανανάθεση)· αφαίρεση του
κριτηρίου επιπέδου αρχείου· διόρθωση της εξαίρεσης ώστε να δέχεται μπλοκ αιτιολογίας·
baseline **145/90**· 45 tests με 5/5 μεταλλάξεις **και** Μ0 meta-test· Layer 1 στο
`run-checks-parallel.js` (CHECK 3.35), Layer 2 στο `firestore-tenant-scope.yml`.
Δουλειά Γ του ADR-745 handoff: και τα 3 αρχεία μετρήθηκαν, όλα νόμιμα.

**(β) 2026-08-05 — ΚΑΝΟΝΑΣ 3 + το ξετύλιγμα του `withConverter`.** Δύο τυφλά σημεία που
βρέθηκαν **μετρώντας**, όχι διαβάζοντας.

**Β1 — R3: το κεντρικό API ήταν το μόνο που κανείς δεν κοιτούσε.** Οι R1/R2 κοιτούν direct
`query()` και Admin SDK. Καμία πύλη — ούτε 3.10, ούτε 3.15, ούτε R1/R2 — δεν κοιτούσε τη
διαδρομή μέσω του **κεντρικοποιημένου** `firestoreQueryService` (ADR-214), δηλαδή ακριβώς
το API που όλος ο κώδικας ενθαρρύνεται να χρησιμοποιεί. Εκεί το φίλτρο μισθωτή σβήνει με
**μία λέξη** (`tenantOverride: 'skip'` ⇒ `buildTenantConstraints` επιστρέφει `[]`).
🔴 **Είναι η τέταρτη επανάληψη του ίδιου σχήματος** («η πύλη κοιτά ένα σχήμα κειμένου· ο
κώδικας γράφτηκε σε άλλο») — με τη διαφορά ότι εδώ το «άλλο σχήμα» είναι το **συνιστώμενο**,
πράγμα που το κάνει χειρότερο, όχι καλύτερο.

Μετρήθηκαν **16** σημεία σε 11 αρχεία ⇒ 12 σημεία R3: **4 σωστά αγνοημένα** (η αυθεντία
`tenant-config.ts` λέει `mode=none`: `SECURITY_ROLES`, `EMAIL_DOMAIN_POLICIES`,
`COUNTRY_SECURITY_POLICIES`, `CONFIG`), **1 unanalyzable** (δυναμικό κλειδί), **3 νόμιμα**
που πήραν ρητή αιτιολόγηση, **4 γνήσια ευρήματα**. Ο κανόνας **δεν απαγορεύει** το `skip` —
απαιτεί **λόγο**, με το ίδιο σύστημα εξαίρεσης του R1/R2.

⚠️ **Δύο άγκυρες εξαίρεσης, όχι μία.** Η πρώτη εκδοχή δεχόταν λόγο μόνο πάνω από τη γραμμή
της **κλήσης** — αλλά οι κλήσεις του service είναι πολυγραμμικές
(`subscribeDoc(key, id, cb, onErr, {…})` πιάνει 8 γραμμές) και ο αναγνώστης γράφει τον λόγο
**δίπλα στο `tenantOverride`**. Απέρριπτε δηλαδή την τεκμηριωμένη εξαίρεση ενώ δεχόταν τη
βιαστική μονόγραμμη — **ακριβώς το σφάλμα που το σχόλιο του `isExempt` προειδοποιεί να μην
επαναληφθεί**, ξαναγραμμένο 40 γραμμές πιο κάτω. Πιάστηκε ζωντανά, στο ίδιο το
`user-settings-repository.ts`.

**Β2 — το `.withConverter()` έκρυβε τη συλλογή.** Το `query(collection(db, X).withConverter(c), …)`
βάζει τη συλλογή στην **έκφραση** της πρόσβασης ιδιότητας, ενώ ο σαρωτής κοιτούσε τα
**ορίσματα** (εκεί βρίσκει μόνο τον converter) ⇒ `unanalyzable` ⇒ η πύλη περνούσε χωρίς να
δει. 🔑 **Το ratchet σημείωμα το χαρακτήριζε «αμέτρητο» και πρότεινε να ξαναγραφούν τα
αρχεία· η μέτρηση ανέτρεψε και τα δύο**: είναι **9** σημεία σε 7 αρχεία, **όλα** σε υπηρεσίες
που έχουν ήδη σωστό `where('companyId')` — δηλαδή η πύλη ήταν τυφλή ακριβώς στον κώδικα που
**περνούσε**. Η θεραπεία ανήκει στο **όργανο** (`resolveCollectionArg` ξετυλίγει αναδρομικά),
όχι σε 9 αρχεία παραγωγής: το ιδίωμα είναι νόμιμο Firestore v9.

**Baseline 145/90 → 150/95.** ⚠️ **Η αύξηση ΔΕΝ είναι χειροτέρευση — είναι ορατότητα**:
`unanalyzable` **198 → 194**, `exempt` **1 → 4**. Τέσσερα από τα +5 είναι τα `skip` χωρίς
λόγο· το πέμπτο ήταν πάντα εκεί και απλώς **εξαφανιζόταν** στο `unanalyzable`. Τα τέσσερα
μπήκαν σε baseline και **όχι** σε σιωπηλή διόρθωση: η αλλαγή τους αλλάζει **συμπεριφορά**
(αν τα έγγραφα δεν φέρουν `companyId`, το φίλτρο αδειάζει την οθόνη) και είναι απόφαση
Giorgio, όχι του πράκτορα. Καταγράφηκαν στο `.claude-rules/pending-ratchet-work.md`.

**(γ) 2026-08-05 — τα 4 `skip` εκκαθαρίστηκαν· βλ. ADR-758.** Η πύλη έκανε τη δουλειά της:
τα έφερε στο φως, αρνήθηκε να τα διορθώσει σιωπηλά, και η εκκαθάριση ξεκίνησε από **μέτρηση**
αντί από ανάγνωση. Η μέτρηση ανέτρεψε τη διάγνωση σε **δύο** σημεία: (α) τα έγγραφα φέρουν
`companyId` σε ποσοστό **100%** — δεν υπήρχε κίνδυνος «κενής οθόνης» από εκεί· (β) ο πραγματικός
κίνδυνος ήταν αλλού, στο **composite index που έλειπε** — το `skip` ήταν το μόνο που έκανε το
`getProperties()` να τρέχει. Στη διαδρομή βρέθηκε ότι τα `properties` rules διάβαζαν
`resource.data.project`, πεδίο που **κανένα έγγραφο δεν έφερε ποτέ** ⇒ το tenant σκέλος ήταν
νεκρό και η συλλογή διαβαζόταν **μόνο** μέσω του δημόσιου, χωρίς `isAuthenticated()`.
Ετυμηγορίες: **2 γνήσια ελαττώματα** διορθωμένα (PROPERTIES, CONTACTS), **1 νόμιμο** με ρητή
αιτιολόγηση (OBLIGATION_TEMPLATES — μεικτή συλλογή με legacy fallback στα rules),
**1 νεκρός κώδικας** διαγραμμένος (`getOwnerContactIds`, 0 καλούντες).
Baseline **150/95 → 146/91**, κλειδωμένη **μετά** την απόδειξη.

Tests **45 → 54**, μεταλλάξεις **5/5 → 7/7** + Μ0.
⚠️ **Το Μ0 έσπασε γράφοντας αυτή τη δουλειά** και άξιζε: στόχευε σκέτο `status: 'violation',`,
που ήταν μονοσήμαντο **όσο υπήρχε ένας κλάδος παράβασης**. Με τον R3 άρχισε να μεταλλάσσει
**τον λάθος κλάδο** ⇒ το meta-test που πιστοποιεί ότι «οι μεταλλάξεις φτάνουν στη μνήμη»
γινόταν κόκκινο για λόγο άσχετο με αυτό που ελέγχει. Στοχεύει πλέον το `detail` του τελικού
κλάδου (μονοσήμαντο· η επανάληψη του `status` υπερισχύει ως τελευταίο κλειδί), άρα **δεν
εξαρτάται από το πλήθος των κανόνων**.

**(ζ) 2026-09-21 — η ΤΕΤΑΡΤΗ μορφή, και τρεις προβλέψεις που η εκτέλεση ανέτρεψε.** Ο R2
μετακινήθηκε στον κοινό αναλυτή αλυσίδας του ADR-870 (αγκύρωση στο **τέρμα**). Πλήρες
σκεπτικό: **§13**.

Σε αριθμούς: προβλεπόταν **146 → ~224 (+53%)**· μετρήθηκε **146 → 145**, και μετά τη
διαλογή **131 / 87**. Προβλέπονταν **78** τυφλά σημεία· ήταν **69** μετά από τρεις
διορθώσεις. Προβλεπόταν ότι ο αναλυτής θα **βάρυνε** το Layer 1· είναι **9× φθηνότερος**
ανά αρχείο (0,231 ms vs 2,135 ms). **Καμία από τις τρεις δεν ήταν ορατή χωρίς εκτέλεση.**

Νέα κατάσταση **`stale-exempt`** (ADR-747 §13.4): ο κανόνας ρωτά πλέον και το αντίστροφο —
*«ποια εξαίρεση δεν εξαιρεί τίποτα;»* — γιατί η **FSE 2025** μετρά **50,8%** suppressions
που δεν καταστέλλουν καμία προειδοποίηση και κρύβουν **μελλοντικές**. Μετρήθηκαν **8** στο
δέντρο ⇒ **ZERO-TOL μόνο στο άγγιγμα**, ποτέ στον αριθμό του ratchet.

Tests **54 → 65**, μεταλλάξεις **7/7 → 10/10** + Μ0. ⚠️ **Δύο υπάρχουσες μεταλλάξεις (Μ5,
Μ8-προδρομος) στόχευαν κείμενο που η μετάβαση διέγραψε** — άγκυρα που δείχνει σε κώδικα

(21 γρ. / 72 tokens) — κεντρικοποιήθηκε. **Η baseline ΔΕΝ κλειδώθηκε**: περιέχει
βελτιώσεις άλλου agent στο κοινό δέντρο.

## 13. Η τέταρτη μορφή: η ρίζα που δένεται σε όνομα (2026-09-21)

### 13.1 Το εύρημα

Η κεφαλίδα του σαρωτή απαριθμούσε **τρεις** μορφές του σχήματος «η πύλη κοιτά ένα σχήμα
κειμένου· ο κώδικας γράφτηκε σε άλλο». Υπήρχε **τέταρτη**, και ο ίδιος ο κανόνας την
κατέτασσε ως *αθώα*:

```ts
const tasksRef = adminDb.collection(COLLECTIONS.TASKS);   // ← εδώ σταματούσε η αλυσίδα
const snap = await tasksRef                                // ← εδώ ζούσαν τα φίλτρα
  .where('reminderDate', '<=', now)
  .where('reminderSent', '!=', true)
  .limit(50).get();
```

Ο R2 αγκύρωνε στο `.collection(X)` και **ανέβαινε**· όταν τα φίλτρα μπαίνουν σε **άλλη
εντολή** δεν έβλεπε κανένα `where()` και αποφαινόταν **«δεν είναι list query»**. Είναι list
query, φιλτράρει, και δεν έχει `companyId`.

### 13.2 Τι αποκάλυψε η μέτρηση — τρεις διορθώσεις του ίδιου αριθμού

Ο αριθμός των τυφλών σημείων **διορθώθηκε τρεις φορές, κάθε φορά με μέτρηση**:

| | σημεία | γιατί έπεσε |
|---|---:|---|
| πρώτη εκτίμηση | 83 | κριτήριο **ανά κλάδο** ⇒ κάθε βοηθός ADR-742 ψευδώς θετικός |
| δεύτερη | 78 | κριτήριο **ανά σημείο** (−5) |
| τρίτη | 73 | **5 σημεία είχαν ήδη** αιτιολογημένη εξαίρεση (−5) |
| **τελική** | **69** | **4 ακόμη θα γίνονταν ΨΕΥΔΩΣ κόκκινα** — §13.3 (−4) |

🔴 **Και η προβολή του ratchet ήταν λάθος κατά ~80.** Το handoff προέβλεπε **146 → ~224
(+53%)**. Μετρημένο αποτέλεσμα της μετάβασης: **146 → 145**, και μετά τη διαλογή **131 / 87**.
Ο λόγος είναι δομικός και δεν ήταν ορατός χωρίς εκτέλεση: ο παλιός R2 εξέπεμπε σημείο για
**κάθε** `.collection()` — **1.325** σημεία — ενώ ο νέος εκπέμπει **ένα ανά εκτελούμενο
ερώτημα** (**615**). Η τέταρτη μορφή **πρόσθεσε** 17 παραβιάσεις· η υπερμέτρηση του παλιού
σαρωτή **αφαίρεσε** 18. *Μια προβολή που μετρά μόνο τη μία κατεύθυνση είναι μισή αριθμητική.*

⚠️ **Και το κόστος ήταν αντίστροφο από την υπόθεση.** Το «ο αναλυτής του ADR-870 κάνει ολικό
σε 4,2s» ήταν κόστος **13.242 αρχείων**. Ανά αρχείο: **0,231 ms** έναντι **2,135 ms** του
σημερινού σαρωτή — **9× φθηνότερος**. Το Layer 1 **ελάφρυνε**.

### 13.3 Τι έπρεπε να αλλάξει για να μη γεννηθεί η πύλη κόκκινη

Η αγκύρωση στο τέρμα είναι **αυτό ακριβώς** που κάνει ορατή την τέταρτη μορφή — και στην
**ίδια** μορφή απομακρύνει το σημείο κρίσης από τη γραμμή όπου ο άνθρωπος γράφει τον λόγο του.

1. **Η αιτιολογία γίνεται δεκτή και στα ΔΥΟ άκρα** (`isExemptAtEither`). Μετρημένο στο
   `entity-audit.service.ts`: αιτιολογία στη γρ. **342**, `.get()` στη γρ. **356** —
   δεκατέσσερις γραμμές, με κώδικα ανάμεσα που κόβει τον αναγνώστη μπλοκ. Ένα άκρο μόνο ⇒
   **4 σημεία / 2 αρχεία** με τεκμηριωμένη εξαίρεση θα γίνονταν ψευδώς κόκκινα: *η πύλη θα
   τιμωρούσε όποιον έκανε ό,τι του ζητήθηκε.* Άγκυρα **Μ8**.
2. **Υποσυλλογή κάτω από `.doc()`** (`docScoped`): στο `contacts/{id}/bank_accounts` ο άξονας
   απομόνωσης είναι η **διαδρομή**, όχι πεδίο — ο γονέας είναι ήδη **ένα** έγγραφο. Ο σαρωτής
   σταματούσε στην εσώτερη `.collection()` **χωρίς ποτέ να κοιτάξει τον παραλήπτη της**, άρα
   υποσυλλογή και ρίζα ήταν **αδιάκριτες**: **6 σημεία / 4 αρχεία** θα ζητούσαν φίλτρο που θα
   ήταν ανοησία. Άγκυρα **Μ9**. ⚠️ Δεν λέει «ασφαλές» — λέει ότι η ερώτηση ανήκει σε **όποιον
   έλυσε το `{id}`**.
3. **Ο κατασκευαστής χωρίς τέρμα** (`includeUnterminated`): `export const q = (db) =>
   db.collection(X).where(…)` δεν έχει `.get()`. Χωρίς δεύτερο πέρασμα, **δύο ζωντανές
   άγκυρες του ADR-866 §2.6.7 έπαψαν να βλέπουν οτιδήποτε** — «δεν το είδα» που μοιάζει με
   «καθαρό», το ίδιο σχήμα με το `0` του N.11 και του N.12. Είναι **opt-in**: το CHECK 3.91
   ρωτά «ποιο ερώτημα **εκτελείται** και θέλει δείκτη;» και ένας κατασκευαστής δεν εκτελεί.
4. **Ανάγνωση ενός εγγράφου** (`.doc(id).get()`) **βγήκε** από την εμβέλεια: δεν είναι
   ερώτημα, δεν μπορεί να επιστρέψει λίστα. Το στένεμα φυλάσσεται από **άγκυρα-σύνορο**: η
   ανάγνωση **ολόκληρης** συλλογής χωρίς `where()` — που επιστρέφει κάθε μισθωτή —
   εξακολουθεί να κρίνεται. *Ένα στένεμα χωρίς σύνορο γίνεται διαρροή.*

### 13.4 Ο φρουρός των αδρανών εξαιρέσεων — γιατί η inline αιτιολογία είναι ασφαλής μόνο μαζί του

Η απόφαση «γράψε αιτιολογία στα νόμιμα, μη φουσκώσεις τη baseline» στηρίζεται στη
βιβλιογραφία — και **η ίδια βιβλιογραφία λέει γιατί δεν αρκεί**:

- Η σύγκριση baseline vs inline καταλήγει ότι *«baseline βοηθά στο onboarding· inline
  suppressions **με αιτιολογία** βελτιώνουν τη μακροπρόθεσμη συντηρησιμότητα»*, και ότι το
  κύριο πρόβλημα της baseline είναι ότι **σαπίζει**.
- Αλλά η **FSE 2025** («An Empirical Study of Suppressed Static Analysis Warnings», 7.357
  suppressions σε 46 έργα, Pylint/Checkstyle/PMD/ESLint) μετρά ότι **50,8% των suppressions
  δεν επηρεάζουν καμία προειδοποίηση**, ότι το πλήθος τους **αυξάνεται μονότονα**, και ότι
  *«μερικά, συμπεριλαμβανομένων των άχρηστων, μπορεί να κρύψουν ακούσια **μελλοντικές**
  προειδοποιήσεις»*.

⇒ Μια εξαίρεση που σήμερα δεν καλύπτει τίποτα είναι **προ-εγκεκριμένο veto σε ό,τι γραφτεί
εκεί αύριο**. Ο κανόνας κρατά πλέον **ποια γραμμή** καταναλώθηκε και αναφέρει τις υπόλοιπες
ως `stale-exempt` — **δική τους κατηγορία**, ώστε να μετριούνται χωρίς να μολύνουν τον
αριθμό που μετρά απομόνωση. Είναι το δόγμα των «αδρανών φρουρών» του N.12
(`ssot:audit --dormant`), στραμμένο στις εξαιρέσεις.

**Μετρήθηκαν 8** στο σημερινό δέντρο (όλες νόμιμες κατά τον λόγο τους, όλες αδρανείς κατά
τον σαρωτή — π.χ. αιτιολογία πάνω από `onSnapshot(doc(...))`, που δεν είναι ερώτημα). Γι'
αυτό η πύλη είναι **⛔ ZERO-TOL μόνο στο άγγιγμα** (σχήμα CHECK 3.15): καθολικό μπλοκ θα τη
γεννούσε κόκκινη, και **μια πύλη που γεννιέται κόκκινη αγνοείται** (ADR-742). Άγκυρα
**Μ10**: αν ο κανόνας χάσει τη μνήμη κατανάλωσης, καταγγέλλει **κάθε** σωστά γραμμένη
εξαίρεση — γίνεται ακριβώς ο θόρυβος που αποτρέπει.

### 13.5 SSoT: ο R2 δεν έχει πια δικό του αναλυτή

Ήταν **δύο** αναλυτές για την **ίδια** αλυσίδα, με **αντίθετη** αγκύρωση — ο ένας στο
`.collection(X)` ανεβαίνοντας, ο άλλος στο τέρμα κατεβαίνοντας — δηλαδή δύο απαντήσεις στην
ερώτηση *«ποιο ερώτημα φεύγει από αυτή τη γραμμή;»*. Ο R2 τρέχει πλέον πάνω στο
`firestore-query-chain.js` (ADR-870): −60 γραμμές, και οι `boundNameOf` /
`isPassedToScopeHelper` / `collectChainedReassignments` **διαγράφηκαν** — η λογική τους ζει
στον κοινό αναλυτή.

🔴 **Και το jscpd βρήκε ό,τι κανένας name-based έλεγχος δεν μπορούσε**: το `enclosingScope`
υπήρχε **δύο φορές**, με ίδια λογική και άλλη μορφοποίηση (21 γρ. / 72 tokens), αόρατο σε
κάθε έλεγχο ονόματος. Κεντρικοποιήθηκε στο `firestore-ast-loaders.js`. Μαζί του ενοποιήθηκε
και το regex της εξαίρεσης σε **μία** συνάρτηση (`exemptionPattern`) — τρία αντίγραφα θα
ήταν τρεις ευκαιρίες να ξανασυμβεί η παγίδα της διπλής διαφυγής, **και δύο από αυτά όντως
την έπαθαν τη στιγμή που γράφτηκαν**.

### 13.6 Η διαλογή: τι ήταν πραγματικά τα 17 νέα σημεία

Διαλογή με **μετρήσιμα σήματα ανά σημείο** (ποτέ ανά αρχείο — αυτό είναι το σφάλμα του
ADR-745 §9.5), και **ανάγνωση κάθε σημείου** πριν γραφτεί αιτιολογία:

| κατηγορία | σημεία | πράξη |
|---|---:|---|
| εργάτης ουράς / cron / migration (καθολικό πέρασμα) | 9 | αιτιολογημένη εξαίρεση |
| δεσμός υπογεγραμμένου token (ο δεσμός **είναι** η εξουσιοδότηση) | 1 | αιτιολογημένη εξαίρεση |
| γονέας **επαληθευμένος πριν** (`resolveOwnedToolDoc`) | 2 | αιτιολογημένη εξαίρεση |
| ανώνυμο endpoint διαγραφής (άξονας = `sessionId`, διπλά ελεγμένος) | 1 | αιτιολογημένη εξαίρεση |
| λειτουργική τηλεμετρία υποδομής (μοναδικός καλών επαληθευμένος) | 1 | αιτιολογημένη εξαίρεση |
| **🔴 γνήσια ευρήματα απομόνωσης** | **2** | **ΔΕΝ αιτιολογήθηκαν — δες §13.7** |

⚠️ **Καμία αιτιολογία δεν λέει «είναι εντάξει».** Καθεμία ονομάζει **τον άξονα απομόνωσης που
ισχύει εκεί**, και όπου υπάρχει, **τη συνθήκη που την ακυρώνει** (π.χ. «αν αυτά τα νούμερα
φτάσουν σε επιφάνεια μισθωτή, γίνονται διαρροή όγκου και η εξαίρεση παύει να ισχύει»).

### 13.7 Τα δύο που έμειναν — και γιατί ΔΕΝ διορθώθηκαν εδώ

1. **`api/ika/employment-records/route.ts:72`** — μέσα σε `withAuth`, με το `ctx.companyId`
   διαθέσιμο, το ερώτημα φιλτράρει σε `projectId` που έρχεται από το **σώμα του αιτήματος**,
   **χωρίς έλεγχο ιδιοκτησίας**. Είναι το σχήμα του ADR-745 §9.5.
   ⚠️ **Η προφανής διόρθωση είναι λάθος**: σκέτο `where(companyId)` θα έκρυβε παλιά έγγραφα
   χωρίς το πεδίο ⇒ **διπλότυπα**. Σωστή πράξη: έλεγχος ιδιοκτησίας του `projectId` **πριν**
   το ερώτημα, όπως ήδη κάνει το `api/storages/route.ts`.
2. **`services/contact/first-contact-invitation.service.ts:214`** — το
   `supersedePreviousInvitations` συγκρίνει **μόνο τον στόχο**, ποτέ τον εκδότη ⇒ άλλη
   εταιρεία ακυρώνει τον ζωντανό σύνδεσμο της πρώτης. **Ερώτημα τομέα, όχι καθαρό bug**: από
   τη σκοπιά του **προσκεκλημένου** είναι το επιθυμητό· από τη σκοπιά του **εκδότη** είναι
   σιωπηλή απώλεια.

🔑 **Και τα δύο έμειναν κόκκινα επίτηδες.** Αιτιολόγηση χωρίς απόφαση θα ήταν ακριβώς το
«ψεύτικο 0» που γέννησε αυτή την πύλη. Η baseline **δεν κλειδώθηκε**: περιέχει **5
βελτιώσεις άλλου agent** στο κοινό δέντρο — το κλείδωμα είναι πράξη του κατόχου.
