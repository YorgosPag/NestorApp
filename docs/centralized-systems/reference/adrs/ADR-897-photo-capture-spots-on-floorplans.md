## 1. Το πρόβλημα

Η δημόσια αγγελία δείχνει φωτογραφίες **και** κατόψεις, αλλά **δίπλα-δίπλα, ασύνδετες** (ADR-841 §7 Α17.2: «δίπλα,
ποτέ μέσα»). Ο επισκέπτης δεν ξέρει **από πού** τραβήχτηκε μια φωτογραφία ούτε **προς τα πού** κοιτάζει. Η Zillow
(και η CubiCasa μέσω Redfin) το λύνει με σημεία πάνω στην κάτοψη ανά όροφο, τονισμένο σημείο + κώνο για την τρέχουσα
φωτογραφία, και κλικ στο σημείο ⇒ άλμα στη φωτογραφία.

## 2. Έρευνα — τι κάνουν οι μεγάλοι (2026-10-01)

| Παίκτης | Πώς τοποθετείται | Τι αποθηκεύει | Τι κρατάμε |
|---|---|---|---|
| **Zillow** 3D Home / Showcase | **αυτόματα**, CV από τα πανοράματα 360° (Zillow Indoor Dataset, CVPR 2021) | πόζα ανά φωτογραφία ως προς την κάτοψη | ✅ η εμπειρία θεατή (πάνελ κάτοψης, σημεία, κώνος, άλμα) |
| **CubiCasa** (Redfin) | AI **+ χειροκίνητη διόρθωση** («Quick Edit»: σύρσιμο θέσης, λαβή κατεύθυνσης, όροφος) | `{x,y}`, όροφος, δωμάτιο, κατεύθυνση | ✅ ο επεξεργαστής: σύρσιμο + λαβή |
| **Revit** κάμερα | χειροκίνητα: σημείο ματιού + **στόχος** + FOV | eye, target, FOV | ✅ **λαβή-στόχος** για την κατεύθυνση · FOV ως πρώτης τάξης πεδίο |
| **3DVista** «radar» · **Kuula** | χειροκίνητα | θέση, σταθερός κώνος | ⚠️ σταθερός κώνος — εμείς από τον φακό |
| **iGUIDE** · **Matterport** | αυτόματα από τη σάρωση | πόζα σταθμού | — (απαιτεί εξοπλισμό σάρωσης) |
| **idealista / Rightmove / Zoopla** | — | στατική εικόνα κάτοψης | — (δεν το έχουν) |

**Συμπεράσματα που δεσμεύουν τον σχεδιασμό:**
1. Όλοι όσοι τοποθετούν αυτόματα έχουν **χειροκίνητη διόρθωση** — η αυτόματη τοποθέτηση **δεν** είναι αξιόπιστη μόνη της.
2. Η πυξίδα του κινητού (`GPSImgDirection`) **μέσα σε κτίριο** είναι αναξιόπιστη (οπλισμός, συσκευές) ⇒ μόνο **πρόταση**.
3. FOV από EXIF: `HFOV = 2·atan(18 / FocalLengthIn35mmFilm)` — σε **όρθια** φωτογραφία η οριζόντια διάσταση είναι 24 mm
   (άρα `12` αντί `18`), αλλιώς ο κώνος βγαίνει ~1,5× φαρδύτερος.
4. Τίποτα αυτόματο δεν δημοσιεύεται χωρίς ανθρώπινη επιβεβαίωση.

## 3. Απόφαση

### 3.1 Δεύτερη δήλωση δίπλα στο σημείο εστίασης — ίδιο κανάλι, κανένα νέο

Το σημείο λήψης είναι **ίδιο είδος γνώσης** με το σημείο εστίασης (ADR-880): ανθρώπινη δήλωση ανά φωτογραφία, δεμένη
στο `FileRecord.id` (ποτέ στη θέση — το ράφι πετά απορρίψεις, άρα `published[i] ≠ sources[i]`). Ακολουθεί **ακριβώς**
την ίδια διαδρομή:

| Στάδιο | Γραφείο | Ιδιοκτήτης (φάκελος) |
|---|---|---|
| Αποθήκευση | `properties/{id}.publishedPhotoCaptureSpots` | `owner_properties/{id}.publishedFileCaptureSpots` |
| Πόρτα | `PropertyPatchSchema` (`property-patch-helpers.ts`) | `ownerPropertyDraftSchema` |
| Ανάγνωση | `agencyMediaDeclaration` → `captureSpots` | `owner-property-from-document` · `ownerListingMediaSources` |
| Πηγή ραφιού | `publishedAgencyMediaSources` | `publishedDossierMediaSources` |
| Ράφι | `PublicShelfSource.{sourceFileId, captureSpot}` → `PublicShelfImage.{sourceFileId, declaredCaptureSpot}` (αδιαφανώς) | ίδιο |
| Προβολή | `withPublishedGallery` → `withCaptureSpots` | ίδιο |
| Δημόσιο | `ListingImage.captureSpot` | ίδιο |

**Απορρίφθηκε**: επέκταση του spatial-tour (ADR-884). Εκείνο είναι για πανοράματα 360° με βαθμονομημένα μέτρα, γράφημα
κόμβων και προσκλήσεις φωτογράφου — υπερβολικά βαρύ για μια επίπεδη φωτογραφία πάνω σε raster κάτοψη.
**Απορρίφθηκε**: νέα συλλογή Firestore. Τα δεδομένα είναι ένας μικρός χάρτης δίπλα στις άλλες δηλώσεις, με τον ίδιο κύκλο
ζωής (αισιόδοξη γραφή, συμφιλίωση, επαναπροβολή).

### 3.2 Το μοντέλο (SSoT: `src/lib/listings/photo-capture-spot.ts`)

```ts
interface PhotoCaptureSpot {      // αποθήκευση
  floorplanFileId: string;        // ποια ΔΗΛΩΜΕΝΗ κάτοψη (όροφος)
  x: number; y: number;           // [0,1] από πάνω-αριστερά της εικόνας κάτοψης
  headingRad: number;             // χώρος εικόνας: 0 = πάνω, δεξιόστροφα (σύμβαση SVG rotate) — ΟΧΙ πυξίδα
  fovRad: number;                 // οριζόντιο πεδίο, [10°, 125°]· προεπιλογή ≈ 69° (κύριος φακός κινητού, 26 mm)
}
interface ListingCaptureSpot {    // δημόσιο
  floorplanIndex: number;         // δείκτης στο floorplans[] του ΙΔΙΟΥ εγγράφου
  x; y; headingRad; fovRad;
}
```

- 🔴 **Καμία εσωτερική ταυτότητα αρχείου στο κοινό.** Η κάτοψη γίνεται **δείκτης** στον γραφέα. Ο δείκτης είναι σταθερός
  επειδή `gallery` και `floorplans` γράφονται μαζί, ατομικά, από τον έναν γραφέα.
- 🔴 **Κάτοψη που δεν βγήκε ⇒ το σημείο πέφτει** (ποτέ κρεμασμένος δείκτης). Η αποθηκευμένη δήλωση **επιβιώνει**, ώστε
  να ξαναφανεί αν η κάτοψη επιστρέψει. Γι' αυτό η πόρτα **δεν** διασταυρώνει «είναι η κάτοψη δηλωμένη;» — αυτό
  το κρίνει η προβολή.
- Το δέσιμο γίνεται **μετά** το πέρασμα δρομολόγησης: μια φωτογραφία μπορεί να έρχεται πριν την κάτοψή της.
- Φωτογραφία χωρίς δήλωση μένει **byte-προς-byte ίδια** (το πεδίο δεν γράφεται, ούτε `null`).
- Ο αναγνώστης (`readListingCaptureSpot`) ξαναελέγχει σχήμα **και** δείκτη: το δημόσιο έγγραφο διαβάζεται ρηχά.
- **Κανένας κρίκος μετανάστευσης** (`public-listing-schema.ts`): ίδιο σκεπτικό με το `focalPoint` — απόν ⇒ «δεν δηλώθηκε».
- Legacy `OwnerProperty.media[]` (dual-read, αποσύρεται στο ADR-866 Φ1.6): **δεν** υποστηρίζεται — το σημείο θέλει
  ταυτότητα κάτοψης, που μόνο ο φάκελος έχει.

### 3.3 Κοινή μηχανή «χάρτης ανά αρχείο» (N.0.2)

Με τη δεύτερη δήλωση ανά φωτογραφία, ο σκελετός ανάγνωσης/ισότητας/αντικατάστασης εξήχθη σε
`src/lib/listings/declared-file-map.ts` (`readDeclaredFileMap` · `sameDeclaredFileMap` · `withDeclaredFileEntry`).
Το `photo-focal-point.ts` και το `photo-capture-spot.ts` είναι λεπτοί κωδικοποιητές πάνω του.

### 3.4 Ο βορράς της κάτοψης (Φ5.2) — SSoT: `src/lib/listings/floorplan-north.ts`

**Έρευνα (2026-10-01):**

| Παίκτης | Πώς δηλώνεται ο βορράς | Τι κρατάμε |
|---|---|---|
| **Revit** | Project North = το «πάνω» του φύλλου · True North = **μία γωνία** (*Rotate True North*, «Angle from Project to True North»). Το κτίριο **δεν** στρίβει | ✅ το μοντέλο: η κάτοψη μένει όπως σχεδιάστηκε, ο βορράς είναι γωνία πάνω της |
| **ArchiCAD** | Project North στο *Location* · σύμβολο βέλους βορρά στη γωνία του σχεδίου | ✅ βέλος στη γωνία, χωρίς να κρύβει το σχέδιο |
| **CubiCasa** | ρόδα πυξίδας στο QuickEdit: στροφή με ποντίκι **ή** τιμή· αυτόματα από το κινητό κατά τη σάρωση | ✅ σύρσιμο του βέλους + ρυθμιστής |
| **Matterport** | προσανατολισμός από την πρώτη σάρωση· δεν αποθηκεύεται αλλαγή· η πυξίδα (plugin) δεν φαίνεται στην κάτοψη | — (αυτό που **δεν** θέλουμε) |
| **iGUIDE** | βέλος βορρά στα σχέδια από τη σάρωση | ✅ βέλος στη δημόσια κάτοψη |

**Απόφαση:**
- `northRad`: γωνία του **πραγματικού** βορρά στον χώρο της εικόνας, **ίδια** σύμβαση με το `headingRad`
  (0 = πάνω, δεξιόστροφα). Ανά **κάτοψη**, όχι ανά αγγελία (δύο όροφοι μπορεί να σαρώθηκαν αλλιώς).
- Αποθήκευση: χάρτης `floorplanFileId → northRad` στην ίδια μηχανή `declared-file-map` —
  `properties/{id}.publishedFloorplanNorth` (γραφείο) · `owner_properties/{id}.publishedFileFloorplanNorth` (ιδιώτης).
  Ταξιδεύει όπως όλες οι δηλώσεις: `PublicShelfSource.northRad` → `CarriedFacts.declaredNorthRad` (μία γραμμή) →
  `withPublishedGallery` **μόνο στον κλάδο `floorplan`** → `ListingImage.northRad` (απόν ⇒ κανένα βέλος).
- **Η σχέση**: `heading(εικόνα) = north(εικόνα) + compass(από βορρά)`. Λύνεται **και προς τις δύο μεριές**:
  - βορράς + πυξίδα ⇒ **πρόταση κατεύθυνσης** (`headingFromCompass`), με κουμπί «Χρήση»·
  - 🏆 **πάνω από CubiCasa/Revit**: κατευθύνσεις που ο άνθρωπος ήδη έβαλε + πυξίδες ⇒ **πρόταση βορρά**
    (`estimateNorthFromCompass`): **κυκλικός** μέσος (ποτέ αριθμητικός — 350° και 10° δίνουν 180°), απόρριψη μίας
    εξαίρεσης >45° όταν υπάρχουν ≥3 δείγματα, και **μέτρο συμφωνίας** (κυκλική τυπική απόκλιση): >30° ⇒ «οι πυξίδες
    διαφωνούν», καμία πρόταση. Ο άνθρωπος δεν χρειάζεται να ξέρει πού είναι ο βορράς.
- **Μαγνητικός vs γεωγραφικός** (απόκλιση ~+5° Α στην Ελλάδα, 2026): **καμία διόρθωση WMM**. (α) Η πυξίδα κινητού μέσα
  σε κτίριο ξεφεύγει >20° σε ~15% των μετρήσεων, άρα τα 5° χάνονται στον θόρυβο· (β) όταν ο βορράς **εκτιμάται από τις ίδιες
  πυξίδες**, η απόκλιση **αλληλοαναιρείται** στην πρόταση κατεύθυνσης· (γ) όλα είναι προτάσεις που ελέγχει άνθρωπος.
  Το `GPSImgDirectionRef` συνεχίζει να διαβάζεται στον διακομιστή, αλλά ο πελάτης δεν το διακρίνει.
- 🔴 **Ποτέ αυτόματη εφαρμογή**: ούτε στη νέα τοποθέτηση. Η πρόταση φαίνεται με την τιμή της· «Χρήση» την περνά
  στο **πρόχειρο** — και αυτό σώζεται μόνο με «Αποθήκευση».

### 3.5 Ατομική αποθήκευση — ΕΝΑ PATCH για σημεία και βορρά (Φ5.2)

Ο χώρος εργασίας κρατά **ένα** πρόχειρο (`CaptureSurvey = { spots, north }`, `lib/listings/capture-survey.ts`) και σώζει
με **μία** πράξη. Στο γραφείο, δύο `usePropertyDeclaration` θα ήταν δύο PATCH με δύο κλειδώματα — το δεύτερο θα
σκόνταφτε στο `saving` του πρώτου και θα **χανόταν σιωπηλά**, ή η αγγελία θα έμενε **μισοαποθηκευμένη**.

**Λύση**: ο κύκλος ζωής εξήχθη σε `usePropertyDeclarationPatch<T>(propertyId, stored, equals, toPatch)` — αισιοδοξία,
κλείδωμα, επαναφορά και συμφιλίωση **μία φορά**, για δήλωση που πιάνει **N πεδία**. Το `PropertyDeclarationPatch`
είναι `Partial<Record<PropertyDeclarationField, unknown>>` — **κλειστό** σύνολο κλειδιών (η πόρτα είναι `.passthrough()`).
Το `usePropertyDeclaration` (ένα πεδίο) έγινε λεπτό περιτύλιγμά του. `useListingCaptureSurvey` = **ένα** `updateProperty`
με `publishedPhotoCaptureSpots` **και** `publishedFloorplanNorth`· το αισιόδοξο αποσύρεται μόνο όταν το έγγραφο
συμφωνήσει **και στα δύο**. Ο ιδιώτης γράφει τα δύο πεδία φόρμας στην ίδια πράξη (`form.setValue` ×2), και τα παίρνει
η **μία** αποθήκευση της φόρμας.
