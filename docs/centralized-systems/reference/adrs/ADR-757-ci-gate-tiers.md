# ADR-757 — Ιεράρχηση πυλών CI: το email που έπαψε να είναι σήμα (CHECK 3.37)

**Κατάσταση:** Ενεργό (ΦΑΣΗ Α υλοποιημένη)
**Ημερομηνία:** 2026-08-05
**Συγγραφέας:** Claude (Opus 5) + Γιώργος Παγώνης
**Κατηγορία:** CI/CD · Παρατηρησιμότητα · Pre-commit Gates
**Σχετικά:** ADR-598 §7 (το μητρώο των πυλών ποιότητας και το ιστορικό τους) · ADR-587 §6.1
(«ένα anchor χωρίς gate είναι σχόλιο» — ο κίνδυνος που αποφεύγεται εδώ) · ADR-752/CHECK 3.36
(ίδιο σχήμα: δύο χειρόγραφοι κατάλογοι, καμία πύλη να τους συγκρίνει) · ADR-744/CHECK 3.34 ·
ADR-747/CHECK 3.35 («η πύλη που έλειπε ανάμεσα σε δύο πύλες») · ADR-740 (deploy Netcup)

## Summary

Ο Γιώργος έκανε push και ήρθαν **9 emails αποτυχίας**. Τα **8** ήταν προϋπάρχοντα κόκκινα από
τις 15/07. Το **1** σήμαινε «**το nestorconstruct.gr σταμάτησε να ενημερώνεται**». Δεν υπήρχε
**κανένας** τρόπος να ξεχωριστούν χωρίς πράκτορα που να διαβάσει logs.

Αυτό είναι *alert fatigue* στην καθαρότερη μορφή του. Η αιτία **δεν** είναι οι κόκκινες πύλες —
είναι ότι **κάθε πύλη μιλάει με την ίδια ένταση**. Μια πύλη τάσης που μετράει κάλυψη τεστ
ουρλιάζει το ίδιο δυνατά με την πύλη που φράζει την παραγωγή.

🔴 **Και ένα από τα 8 ήταν ψεύτικο**: το `Bundle-Size Ratchet` ήταν κόκκινο από 01/08 όχι επειδή
μεγάλωσε το bundle, αλλά επειδή **πέθαινε από OOM πριν προλάβει να μετρήσει**. Το bundle
μεγάλωνε **αμέτρητο επί 4 ημέρες, πίσω από ένα κόκκινο που έδειχνε ότι κάποιος κοιτάει.**

> **Ο κανόνας που προκύπτει:** *μια πύλη που πέφτει για λάθος λόγο κρύβει τον σωστό.*
> Κόκκινο χωρίς **επαληθευμένη αιτία** δεν είναι σήμα — είναι θόρυβος που μοιάζει με σήμα.

## 1. Τι έδειξε η ανατομία του συγκεντρωτή

Υπήρχε ήδη υποδομή: το `.github/workflows/ci-health-report.yml` (98 γρ.), που αυτοπεριγραφόταν
ως *«the durable SSoT of CI failures»*. **Είχε δύο δομικά ελαττώματα**, και τα δύο μετρημένα:

### 1.1 🔴 Η πύλη της παραγωγής ΔΕΝ παρακολουθούνταν

Ο συγκεντρωτής άκουγε **χειρόγραφη λίστα 18 ονομάτων**, με το σχόλιο *«adding a new gate = add
its name below»*. Το δέντρο είχε **26 ενεργά workflows**. Οι **7** που έλειπαν:

| αρχείο | πύλη | tier σήμερα |
|---|---|---|
| `docker-build.yml` | **Build & Deploy Docker Image** | **1 — ΠΑΡΑΓΩΓΗ** |
| `barrel-deadcode-ratchet.yml` | Barrel-aware Dead-export (3.30) | 2 |
| `capability-anchors.yml` | DXF Entity Capability Anchors (5C) | 2 |
| `dxf-tsc-ratchet.yml` | DXF Viewer TS Error (3.29) | 2 |
| `firestore-tenant-scope.yml` | Firestore Tenant Scope (3.35) | 2 |
| `i18n-shell-slice.yml` | i18n Shell Slice Freshness (3.34) | 2 |
| `storage-rules.yml` | Storage Rules | 2 |

Δηλαδή: **τη νύχτα που σταμάτησε η παραγωγή, το «SSoT των αποτυχιών CI» δεν το κατέγραψε καν.**
Και οι 7 είχαν προστεθεί **μετά** τη σύνταξη της λίστας. Ίδιο σχήμα με τις δύο λίστες namespace
του CHECK 3.34, που είχαν αποκλίνει **κατά 63** χωρίς καμία πύλη να τις συγκρίνει.

> **Οδηγία γραμμένη σε σχόλιο δεν είναι πύλη.**

### 1.2 🔴 Ήταν ημερολόγιο, όχι συγκέντρωση

`createComment` σε **κάθε** αποτυχία. Καμία αποδιπλοποίηση ανά `(πύλη, commit)`, **καμία**
επίλυση όταν μια πύλη ξαναπρασινίζει, **κανένα** κλείσιμο. Με 8 μόνιμα κόκκινα αυτό δίνει
**8 νέα σχόλια σε κάθε push** — η ίδια πλημμύρα, μετακομισμένη από το inbox στο Issue #5
(επαληθευμένο: 4 σχόλια σε 1 λεπτό, 31/07).

## 3. Η απόφαση

### 3.0 🔴 Ο δρόμος που ΔΕΝ πήραμε — και γιατί

Η προφανής υλοποίηση της ιεράρχησης είναι: *«τα Tier 2/3 να μην αποτυγχάνουν (exit 0 +
αναφορά), ώστε μόνο το Tier 1 να στέλνει email»*. **Απορρίφθηκε.**

Αυτό ακριβώς έπαθε το `coverage-ratchet.yml` με `continue-on-error`: **11 tests έμειναν κόκκινα
στο main επί ~6 commits** επειδή καμία πύλη δεν τα έτρεχε με δόντια (ADR-587 §6.1). Μια πύλη
που δεν αποτυγχάνει ποτέ **παύει να είναι πύλη**. Η ιεράρχηση επιτρέπεται να μετακινήσει την
**ένταση της ειδοποίησης**· δεν επιτρέπεται να αφαιρέσει το **μπλοκάρισμα**.

**Άρα: καμία πύλη δεν έχασε δόντια. Άλλαξε το ΜΕΣΟ ΜΕΤΑΦΟΡΑΣ, όχι η αυστηρότητα.**

### 3.1 Τρία tier — SSoT: `.ci-gate-tiers.json`

| Tier | Τι είναι | Πολιτική | Πλήθος |
|---|---|---|---|
| **1 — ΠΑΡΑΓΩΓΗ** | Κόκκινο = το nestorconstruct.gr δεν ενημερώνεται | Ειδοποίηση σε **μετάβαση** (έσπασε / αποκαταστάθηκε) | **1** |
| **2 — ΟΡΘΟΤΗΤΑ** | Κόκκινο = ελάττωμα στο main που δεν φαίνεται στην οθόνη | Πίνακας + σχόλιο **μόνο όταν αλλάζει** το σύνολο | **21** |
| **3 — ΤΑΣΕΙΣ** | Μετρικές που κινούνται αργά (κάλυψη, πολυπλοκότητα) | **Μόνο** πίνακας — ποτέ ειδοποίηση | **4** |

Κάθε εγγραφή φέρει `file`, `name`, `tier` και **`why`** — μία γραμμή που λέει *τι σπάει αν
αυτή η πύλη είναι κόκκινη*. Το `why` είναι **υποχρεωτικό**: το tier είναι απόφαση, και απόφαση
χωρίς αιτιολόγηση γίνεται cargo cult στο επόμενο refactor.

### 3.2 🌟 Το tier μπαίνει στο ΙΔΙΟ ΤΟ ΟΝΟΜΑ

Το GitHub στέλνει email ανά αποτυχημένο workflow και η ρύθμιση ειδοποιήσεων είναι **καθολική
ανά χρήστη** — δεν ρυθμίζεται ανά workflow. Άρα η διάκριση **δεν** μπορεί να γίνει από
ρυθμίσεις. Μπορεί όμως να γίνει από το **θέμα του email**, γιατί το θέμα περιέχει το όνομα:

```
Run failed: T1 🚀 Build & Deploy Docker Image - main (db2ca8e)   ← σταμάτησε η παραγωγή
Run failed: T2 📦 Bundle-Size Ratchet (ADR-598 G6) - main (…)     ← ορθότητα, όχι επείγον
Run failed: T3 🧪 Coverage Floor Ratchet (ADR-598 G3) - main (…)  ← τάση
```

Και τα 25 workflows μετονομάστηκαν σε `T<tier> <παλιό όνομα>`. Κόστος: μία γραμμή ανά αρχείο,
**μηδέν** συζεύξεις (μετρήθηκε: κανένα badge, κανένα required check, οι αναφορές σε docs είναι
πεζός λόγος). Κέρδος: η ιεράρχηση φαίνεται στο **inbox**, στο **Actions UI** και στη **λίστα
checks του commit** — χωρίς καμία ρύθμιση, χωρίς κανένα εργαλείο.

**Το πρόθεμα δεν μπορεί να αποκλίνει από το μητρώο**: το CHECK 3.37 το επιβάλλει (`tier-prefix-drift`).

### 3.3 Ο συγκεντρωτής: προβολή, όχι συσσώρευση

Ο `ci-health-report.yml` ξαναγράφτηκε. Η κατάσταση **ξαναϋπολογίζεται** από το Actions API για
κάθε πύλη του μητρώου — **δεν υπάρχει πια λίστα να ξεχαστεί**, και η κατάσταση **δεν μπορεί να
αποκλίνει** επειδή δεν συσσωρεύεται.

| | πριν | τώρα |
|---|---|---|
| πηγή | χειρόγραφη λίστα 18 | `.ci-gate-tiers.json` (26), φυλασσόμενο από CHECK 3.37 |
| μοντέλο | append-only σχόλια | **προβολή** σε σώμα issue, ξαναγραμμένο κάθε φορά |
| σταθερό κόκκινο | 8 σχόλια/push | **σιωπή** |
| επίλυση σε πράσινο | ποτέ | σχόλιο «αποκαταστάθηκε» |
| «ποιος το έσπασε;» | — | **culprit**: ανεβαίνει στο πρώτο συνεχόμενο κόκκινο → commit + συγγραφέας |
| σκανδάλη | 18 × κάθε ολοκλήρωση | **Tier 1** ανά τρέξιμο · υπόλοιπα σε ημερήσιο πέρασμα (05:00 UTC) |

**Ο μηχανισμός της σιωπής:** η ενημέρωση **σώματος** issue δεν στέλνει ειδοποίηση στο GitHub —
μόνο τα **σχόλια** στέλνουν. Άρα ο πίνακας κατάστασης ανανεώνεται αθόρυβα και το σχόλιο
γράφεται **μόνο σε μετάβαση**. Σταθερή κατάσταση ⇒ μηδέν σχόλια ⇒ μηδέν email. Αυτό είναι
αγκυρωμένο σε test («ΣΤΑΘΕΡΟ ΚΟΚΚΙΝΟ ⇒ ΚΑΜΙΑ ΜΕΤΑΒΑΣΗ»).

⚠️ **Ο ίδιος ο συγκεντρωτής δεν έχει tier και δεν παρακολουθεί τον εαυτό του** (βρόχος
`workflow_run`). Αν σπάσει, αποτυγχάνει κανονικά και στέλνει email — **σκόπιμα**: χαλασμένο
όργανο πρέπει να ουρλιάζει, αλλιώς η σιωπή του διαβάζεται ως «όλα καλά».

## 4. CHECK 3.37 — η πύλη που φυλάει τις πύλες

**Εννέα ρητές καταστάσεις**, καμία σιωπηλή απόρριψη:

| κατάσταση | τι σημαίνει |
|---|---|
| `unregistered` | workflow χωρίς tier ⇒ **καμία πολιτική ειδοποίησης** |
| `orphan-registry` | εγγραφή χωρίς αρχείο ⇒ **νεκρός φρουρός** |
| `name-drift` | μητρώο ≠ αρχείο ⇒ ο συγκεντρωτής **δεν θα ταιριάξει ποτέ** |
| `tier-prefix-drift` | το όνομα δεν φέρει το tier του ⇒ **το email δεν ξεχωρίζεται** |
| `unwatched-tier1` | **ΤΟ ΑΡΧΙΚΟ ΣΦΑΛΜΑ** — Tier 1 εκτός λίστας ⇒ **αόρατη αποτυχία παραγωγής** |
| `ghost-watch` | παρακολουθείται ανύπαρκτο όνομα ⇒ **σιωπηλά ανενεργό** |
| `watch-not-tier1` | μη-Tier-1 με σκανδάλη ανά τρέξιμο ⇒ σπατάλη runner σε κάθε push |
| `invalid-entry` | ελλιπής/διπλή εγγραφή (λείπει `why`, tier εκτός 1..3, διπλό `file`) |
| `no-tier1` | κανένα Tier 1 ⇒ **ιεράρχηση χωρίς κορυφή** |

- **Layer 1** — pre-commit, Phase 1 worker. Σκανδάλη: staged `.github/workflows/**`,
  `.ci-gate-tiers.json`, `scripts/lib/ci/**`. Καθαρό in-memory Node σε ~27 μικρά αρχεία.
- **Layer 2** — `.github/workflows/ci-gate-tiers.yml`, **χωρίς συνθήκη**. Υπάρχει επειδή ένα
  workflow μπορεί να μπει στο δέντρο χωρίς να περάσει από το Layer 1 (merge, ξένο commit,
  επεξεργασία στο github.com).
- **ΔΕΝ είναι ratchet — καμία baseline, ποτέ.** «Ανεκτό πλήθος απαρατήρητων πυλών» σημαίνει
  ανεκτό πλήθος αόρατων αποτυχιών παραγωγής.
- Παράκαμψη: `SKIP_CI_TIER_COVERAGE=1` (με λόγο).
- Tests: `npm run test:ci-gate-tiers` — **31 tests, 9/9 μεταλλάξεις + Μ0** στο ζωντανό δέντρο.

### 4.1 Ο αναγνώστης YAML είναι σκόπιμα αυστηρός

Δεν προστέθηκε εξάρτηση `yaml`/`js-yaml` για δύο πεδία (N.5). Ο αναγνώστης
(`scripts/lib/ci/workflow-meta.js`) δέχεται **μόνο** το σχήμα που γράφουν τα ίδια τα workflows
και **πετάει** σε ό,τι δεν καταλαβαίνει. 🔴 **Η παγίδα που αποφεύγεται ρητά** είναι αυτή που
γέννησε φάντασμα-namespace στο CHECK 3.36: οι γραμμές-σχόλια αφαιρούνται **πριν** από κάθε
ανάλυση, και η ένταξη σε μπλοκ γίνεται με **εσοχή** (δομή), όχι με «η επόμενη γραμμή που
ταιριάζει». Και τα δύο έχουν αντίστοιχο test με **εχθρικό** fixture.

## 5. Τι ΔΕΝ κάνει αυτό (ρητά)

- **Δεν διορθώνει καμία κόκκινη πύλη.** 8 ήταν κόκκινες πριν, 8 είναι κόκκινες μετά. Αυτό είναι
  η ΦΑΣΗ Β. Η ΦΑΣΗ Α κάνει το κόκκινο **αναγνώσιμο**, όχι λιγότερο.
- **Δεν εμποδίζει το email των Tier 2/3.** Το κάνει **διακριτό** (πρόθεμα στο θέμα). Ο Γιώργος
  μπορεί να το ολοκληρώσει με ένα φίλτρο Gmail — «θέμα περιέχει `Run failed: T2` ή
  `Run failed: T3` → παράλειψη εισερχομένων, ετικέτα CI» και `T1` → αστέρι. Εναλλακτικά,
  ολική απενεργοποίηση email του Actions (GitHub → Settings → Notifications → Actions), οπότε
  ο πίνακας κατάστασης γίνεται το **μοναδικό** κανάλι. **Και τα δύο είναι δικές του ενέργειες**
  — δεν γίνονται από το repo.
- **Δεν παρακολουθεί PR runs.** Η προβολή είναι για το `main` (`CI_HEALTH_BRANCH`). Οι
  αποτυχίες σε PR είναι ήδη ορατές στο ίδιο το PR.
- **Δεν ξέρει *γιατί* κοκκίνισε μια πύλη** — μόνο *πότε* και *από ποιο commit*. Το «ψεύτικο
  κόκκινο» του §Summary (OOM που μοιάζει με υπέρβαση bundle) **θα ξαναπερνούσε** από εδώ ως
  κανονικό κόκκινο. Η θεραπεία του είναι η ΦΑΣΗ Β, κατά περίπτωση.

### 7.2 Πύλη #1 — 🧮 Type-Complexity: τι έγινε στις 05/08

**Πλήρης τεκμηρίωση: ADR-598 §7, εγγραφή 2026-08-05.** Εδώ μόνο το μάθημα της ΦΑΣΗΣ Β:

> **Το πρωτόκολλο `VERIFY → DIAGNOSE → FIX` κόλλησε στο DIAGNOSE — και αυτό ήταν το εύρημα.**

Η πύλη ήταν κόκκινη **13 συνεχόμενες εκτελέσεις** και **δεν υπήρχε τρόπος** να διαγνωστεί:
το `measure()` κρατούσε την έξοδο του `tsc` σε μεταβλητή και **την πετούσε** πριν πετάξει το
σφάλμα. Δεν ήταν δύσκολο ερώτημα — **η πληροφορία δεν υπήρχε πουθενά**.

🔴 **Η υποψία OOM του handoff §3.6 ΔΕΝ επιβεβαιώθηκε — η εύκολη εκδοχή της καταρρίφθηκε.**
Φυσικό πείραμα στα **ίδια** commits: το `ts-error-gate.yml` τρέχει **το ίδιο** `npx tsc --noEmit`
στο **ίδιο** project, στον **ίδιο** runner, **χωρίς κανένα `NODE_OPTIONS`**, και **ολοκληρώνει σε
2m52s**. Άρα σκέτο `tsc` **χωράει** στο default ταβάνι, ενώ το G14 πεθαίνει στα 5m17s με 6144 MB.
Αν είχα «διορθώσει» σηκώνοντας τη μνήμη, θα είχα ίσως πρασινίσει την πύλη **χωρίς να ξέρω γιατί**.

**Άρα η διόρθωση δεν ήταν μνήμη — ήταν να μιλήσει η πύλη:** ένας κοινός εκκινητής `tsc`
(`scripts/lib/tsc-runner.js`) με **6 ρητές καταστάσεις**, κατά το τετράπτυχο των **Monitoring
Plugins/Nagios**: **CRITICAL** = ο έλεγχος έτρεξε και το πράγμα είναι κακό · **UNKNOWN** = ο
έλεγχος **δεν μπόρεσε να τρέξει**. Και τα δύο κλείνουν την πύλη, αλλά **δεν είναι το ίδιο
μήνυμα** — η σύγχυσή τους είναι που κόστισε τις 9 μέρες.

**Παράπλευρα ευρήματα που δεν έψαχνα** (και τα τρία της ίδιας οικογένειας «0 = κανείς δεν κοίταξε»):

1. 🔴 **ADR-027 ψευδώς πράσινο**: κατάρρευση του `tsc` ήταν δυσδιάκριτη από «0 σφάλματα» ⇒ η πύλη
   πανηγύριζε `Delta: -3005 (you fixed 3005 errors!)` για μέτρηση που δεν έγινε.
2. 🔴 **CHECK 3.28 δομικά τυφλό στο `scripts/`**: `format: ["typescript","tsx"]` ⇒ κανένα `.js`
   δεν σαρώθηκε ποτέ. Ο έλεγχος N.18 επέστρεψε «0 clones σε **0 αρχεία**».
3. ⚠️ **Τέσσερα ταβάνια μνήμης** σε τέσσερα σημεία, με σχόλιο που ισχυριζόταν ότι «mirror» το ένα
   το άλλο. Ποτέ δεν ίσχυε. Πλέον **παράγεται** από τη RAM του μηχανήματος, σε **ένα** σημείο.

⚠️ **Η πύλη ΔΕΝ είναι πράσινη — έγινε αναγνώσιμη.** Η επόμενη εκτέλεση θα **ονομάσει** την
κατάσταση. Αν προκύψει μέτρηση με υπέρβαση budget (πιθανό — ήταν στο **98,6%** πριν 80 commits),
αυτό είναι **γνήσιο εύρημα**, όχι αφορμή για reseed.

### 7.1 🌟 Δύο ιδέες πέρα από την τρέχουσα πρακτική (για ΦΑΣΗ Β/Γ)

1. **Baseline με ΛΗΞΗ.** PHPStan, ESLint, detekt, Android lint — **κανένα** baseline δεν λήγει.
   Έτσι το χρέος γίνεται μόνιμο: η `.barrel-deadcode-baseline.json` έχει **1.587** νεκρά
   exports που κανείς δεν θα κοιτάξει ποτέ. Πρόταση: κάθε εγγραφή baseline φέρει **ιδιοκτήτη +
   ημερομηνία λήξης**· η πύλη κοκκινίζει **όταν λήξει**, όχι μόνο όταν αυξηθεί. Το χρέος γίνεται
   μητρώο με προθεσμία, όχι σιωπηλό συγχωροχάρτι.
2. **Culprit attribution σε ratchets.** Η Google το κάνει για tests· σε ratchet είναι
   **ευκολότερο**: νέο εύρημα → αρχείο+γραμμή → `git blame` → commit+συγγραφέας, αυτόματα μέσα
   στην αναφορά. Σήμερα η πύλη λέει «43 νέα dead exports» και κανείς δεν ξέρει από ποιο από τα
   ~100 commits. *(Το ίδιο μοτίβο υλοποιήθηκε ήδη στον συγκεντρωτή, §3.3.)*
