## 1. Το πρόβλημα

Μερικές όψεις **δεν μπορούν** να ακούσουν τα δεδομένα τους: παράγονται στον server από πολλές πηγές, **φιλτραρισμένες ανά
θεατή** (ακροατήριο, ρόλος, κλάση ιδιωτικότητας), και οι συλλογές τους είναι deny-all επειδή το φίλτρο **δεν εκφράζεται
σε κανόνα** (η Firestore δεν κρύβει πεδία: «you either retrieve the full document, or you retrieve nothing»). Ένα
`onSnapshot` εκεί θα διέρρεε ό,τι κρύβει το ακροατήριο. Αποτέλεσμα: η οθόνη ενημερωνόταν μόνο με F5 (ADR-901 Π5).

## 2. Η αρχή

> **Μια όψη λαμβάνει σήμα αν και μόνο αν η εγγραφή που άλλαξε — πριν ή μετά — είναι ορατή σε αυτήν.**
> Το σήμα **δεν κουβαλά περιεχόμενο**, μόνο έναν αριθμό. Η αλήθεια διαβάζεται **πάντα** από τον server.

Ο αριθμός είναι πληροφορία **χρονισμού**: σήμα στον δικηγόρο του αγοραστή όταν δουλεύει η πλευρά του πωλητή θα του έλεγε
*πότε*. Γι' αυτό η κρίση «ποιες όψεις» ρωτά τους **ίδιους** κριτές ορατότητας που παράγουν την όψη — ποτέ δεύτερη λογική.

## 3. Η έρευνα

| Ποιος | Τι κάνει | Τι κρατάμε |
|---|---|---|
| **Figma LiveGraph** | ξεκίνησε με ενημέρωση αποτελεσμάτων (IVM) και **πέρασε σε invalidate + refetch** — τα σύνθετα ερωτήματα (σελιδοποίηση, συγκεντρωτικά) δεν συντηρούνται· invalidator που διαβάζει το change log | invalidate + refetch· η όψη μας είναι ακριβώς «σύνθετο ερώτημα» |
| **Asana Luna** | reactive queries με ακύρωση | ίδιο σχήμα |
| **Linear sync engine** | μονοτονικό `lastSyncId` · deltas φιλτραρισμένα **ανά δικαιώματα** (sync groups) | αναθεώρηση ανά όψη · ακροατήριο στο σήμα — **και** στον χρονισμό |
| **Transactional outbox** (AWS · microservices.io) | το γεγονός γράφεται στην **ίδια** συναλλαγή με την αλλαγή | πράξη χωρίς σήμα / σήμα χωρίς πράξη = δομικά αδύνατα |
| **Firestore triggers** | at-least-once ⇒ ιδεμποτικός αποδέκτης | διπλή αύξηση = μία περιττή ανάγνωση, ποτέ λάθος εικόνα |
| Procore / Aconex | δεν βρέθηκε δημόσια τεκμηρίωση ζωντανής ενημέρωσης καταλόγων | — (δηλώνεται, δεν υποτίθεται) |

🏆 **Πού πάμε παραπέρα**: (1) μηδέν πλάγιο κανάλι χρονισμού (το Linear φιλτράρει τα δεδομένα, όχι τον χρονισμό)·
(2) η όψη **κουβαλά** την αναθεώρησή της ⇒ η δική μου πράξη δεν φέρνει δεύτερη ανάγνωση· (3) **ρολόι λήξης** στην όψη
(`freshUntil`) αντί για polling — ο client ξαναρωτά **ακριβώς** όταν μπαγιατεύει μόνη της (αλλαγή ημέρας · λήξη πρόσβασης).

## 4. Η απόφαση

### 4.1 Ένα έγγραφο ανά **όψη** (όχι ανά οντότητα, όχι ανά χρήστη)

`conveyance_view_signals/{cvs_…}` — `{ revision, changedAt, <κάτοχος> }`. Το id είναι **ντετερμινιστικό** (`cvs`,
`generateDeterministicConveyanceViewSignalId(viewSignalSeed(view))`): γραφέας και listener το **υπολογίζουν** — κανένα ερώτημα,
κανένας δείκτης, κανένα `list`.

| Όψη | Σπόρος | Κάτοχος (κανόνας `get`) |
|---|---|---|
| οικοδεσπότης — **ανά ακίνητο** (η όψη ζητείται ανά ακίνητο, άρα και το **άνοιγμα** υπόθεσης φτάνει) | `conveyance-view:host:{companyId}:{propertyId}` | `belongsToCompany(companyId)` ‖ super admin |
| συμμετοχή | `conveyance-view:engagement:{engagementId}` | `isOwner(uid)` — η αρχή του `engagements` |

Κανόνας: `get` μόνο με `isAuthenticated()` **και** (`resource == null` ‖ κάτοχος), με ρητό `'uid' in` / `'companyId' in`
(το κλειδί του εγγράφου διαλέγει την ερώτηση κατόχου — αλλιώς token με `companyId: null` θα διάβαζε ξένο σήμα
συμμετοχής). `list` / γραφή: `false`. Το `resource == null` κρατά τον listener ζωντανό πριν από την πρώτη αύξηση.

### 4.2 Ο ΕΝΑΣ γραφέας, μέσα στη συναλλαγή

`signalViewsInTx(tx, db, views)` → `tx.set(ref, { κάτοχος, revision: increment(1), changedAt: serverTimestamp() }, { merge })`.
`signalCaseChangeInTx(tx, db, change, viewers)` = η κρίση (`viewsAffectedBy`) + η γραφή. Οι γενικοί γραφείς που **δεν**
ξέρουν τον τομέα δέχονται το σήμα ως **υποχρεωτική** παράμετρο ή άγκιστρο (βλ. ADR-901 §14.8): ο γραφέας συμμετοχών
(`EngagementRosterSignal`) και η μηχανή προσκλήσεων (`InvitationTxObserver` · `onDecline`).

### 4.3 Η όψη κουβαλά τη φρεσκάδα της (`ViewFreshness`)

`{ revision, freshUntil }`. Η `revision` διαβάζεται **πριν** από κάθε ανάγνωση δεδομένων της όψης — ή **μέσα** στη
συναλλαγή της πράξης που την επιστρέφει (`readViewRevisionInTx` + 1). Έτσι η όψη είναι πάντα **τουλάχιστον** τόσο φρέσκια
όσο ο αριθμός της: ποτέ μόνιμα μπαγιάτικη, ποτέ διπλή ανάγνωση για τη δική μου πράξη.

### 4.4 Client: ΕΝΑ hook + καθαρός ελεγκτής

`useServerViewSignal({ source, revisionOf, freshness, fetch, isHeld })` πάνω στο `useLiveDocument` (ADR-867 Β7 — δουλεύει
και για άνθρωπο **χωρίς** εταιρεία). Ο ελεγκτής (`createServerViewRefresh`, καθαρός):

| Κανόνας | Γιατί |
|---|---|
| ανάγνωση μόνο όταν `σήμα > αναθεώρηση όψης` | η δική μου πράξη επέστρεψε ήδη φρέσκια όψη |
| μία ανάγνωση τη φορά + μία επόμενη | ριπή σημάτων ⇒ ≤ 2 αναγνώσεις |
| συνένωση 250ms | πράξη + δεύτερη αύξηση (π.χ. ακύρωση + κλείσιμο συμμετοχών) ⇒ μία |
| `isHeld` / `release` | όσο εκκρεμούν αισιόδοξες εντολές, η ανάγνωση **περιμένει** — δεν πατά μη επιβεβαιωμένο optimistic |
| αποτυχία ⇒ καμία άμεση επανάληψη | κανένας βρόχος· ξαναδοκιμάζει το επόμενο σήμα / ορατότητα / ρολόι |
| `force()` σε ορατότητα καρτέλας · `online` · `freshUntil` | δίχτυ για ό,τι δεν φτάνει ως σήμα |
| συνδρομή **μόνο** όταν η όψη φορτώθηκε (`'pending'`) | αλλιώς το πρώτο σήμα θα έφερνε ανάγνωση παράλληλα με την αρχική |

Η αποδοχή της όψης είναι **μονοτονική** (`isOlderHostView` · `isOlderEngagedView`): αργή ανάγνωση που φτάνει δεύτερη δεν
γυρίζει πίσω ούτε την οθόνη ούτε τη βάση του CAS (`version`).

### 4.5 Ασφαλής εκφυλισμός

Χωρίς ανάπτυξη των κανόνων ο listener παίρνει `permission-denied` ⇒ `absent` ⇒ η σελίδα συμπεριφέρεται **όπως πριν**
(+ δίχτυ ορατότητας). Καμία οθόνη δεν σπάει από τη σειρά deploy — αλλά η **σωστή** σειρά είναι κανόνες → κώδικας (§7).

## 5. Τι απορρίφθηκε

| Εναλλακτική | Γιατί όχι |
|---|---|
| `onSnapshot` στις συλλογές της όψης | διαρροή ακροατηρίου — οι κανόνες δεν φιλτράρουν πεδία ούτε εκφράζουν `visibleTo` |
| ειδοποιήσεις ως σήμα | δεν ειδοποιεί κάθε πράξη (σφραγισμένη παράδοση, απόσυρση, εντολές)· οι **προτιμήσεις** του χρήστη θα έκοβαν το realtime |
| ένα σήμα ανά οντότητα για όλους | πλάγιο κανάλι χρονισμού προς την άλλη πλευρά |
| σήμα ανά **χρήστη** (fan-out) | η όψη του οικοδεσπότη είναι **ίδια** για όλα τα μέλη του χώρου — ένα σήμα, όχι Ν |
| SSE / WebSocket από Netcup | δεύτερη υποδομή pub/sub· η Firestore είναι ήδη το ζωντανό κανάλι, με κανόνες |
| polling | καθυστέρηση ή κόστος — το `freshUntil` καλύπτει το χρονικό, τα σήματα τα υπόλοιπα |
| IVM (ενημέρωση της όψης κομμάτι-κομμάτι) | ό,τι εγκατέλειψε το Figma — η όψη είναι σύνθετη και ανά θεατή |
| νέα πύλη pre-commit «ένας γραφέας» | ίδια εγγύηση από άγκυρα (Α38) + **δομική** (υποχρεωτική παράμετρος) χωρίς τέταρτο αντίγραφο του κώδικα AST των 3.87/3.88/3.89 — ανοιχτό προς απόφαση (§8) |

## 6. ⏳ Στάδιο 3 — αλλαγές που **δεν** γράφει ο τομέας (CDC)

Η όψη της υπόθεσης εξαρτάται και από εγγραφές **άλλων** γραφέων: αρχεία-τεκμήρια (`files` — client **και** πολλές διαδρομές
server), ακίνητο (`name` · `type` · `linkedSpaces` · `commercial.legalPhase` · `commercial.owners`), έργο
(`landownerContactIds` · `linkedCompanyId`). Μόνο ένας **Firestore trigger** τα βλέπει όλα (Figma: invalidator πάνω στο log).

🔴 **Μετρημένο εμπόδιο**: η κρίση «φτάνει αυτό το αρχείο στον επαγγελματία;» (`decideEngagedEvidenceReach` · `readContainerState`)
κουβαλά κλειστότητα εισαγωγών (`authority` · `capability-authority` · `file-record`) που **δεν** προβάλλεται στα Functions
(ADR-874) χωρίς να γίνει δεύτερη μηχανή. Πρόταση: **trigger ως αναμεταδότης** (υπογεγραμμένο HMAC webhook, μοτίβο
Stripe/GitHub) προς εσωτερική διαδρομή του Next.js, όπου η κρίση τρέχει με τον **ίδιο** κώδικα· ευρετήριο εξαρτήσεων
`conveyance_cases.dependencyKeys` (+ δείκτης, CHECK 3.91). Απαιτεί μυστικό σε Functions **και** Netcup και deploy Functions —
**απόφαση Giorgio**. Μέχρι τότε: δίχτυ ορατότητας + `freshUntil`.
